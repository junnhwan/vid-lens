## 体验问题

### 1. 上传后视频库没有马上显示新视频

- **我做了什么：** 一次上传了三个视频。
- **我看到什么：** 上传完成后，视频库没有立即出现这三个视频；手动刷新后才看见。
- **对使用的影响：** 上传结果不够确定，容易让人以为文件没有传上去。
- **建议改进：** 上传成功后自动刷新视频库和工作台列表，或在上传结果中提供明确入口查看新视频。
- **排查线索：** 三个文件的合并请求都成功，但上传后没有马上重新请求视频列表；代码中上传弹窗的成功回调没有接到父页面，列表也只在页面首次打开时加载。

### 2. 上传成功提示与实际处理状态不一致

- **我看到什么：** 上传弹窗提示任务已创建并进入队列，但当时三个视频只是完成上传，还没有开始转写或生成摘要。
- **对使用的影响：** 用户可能等待自动处理，却不知道还需要到视频详情页手动开始。
- **建议改进：** 上传成功提示只说明“视频已上传”；如果处理需要用户另行启动，应直接写清楚，并给出“开始转写”等下一步操作。
- **排查线索：** 当时视频已入库，但没有对应的处理任务记录或队列消息；视频详情页提供单独启动转写和摘要的操作。

### 3. 模型服务地址填写方式不清楚

- **我遇到什么：** 不同服务和软件对地址的要求不一样：有的填主域名，有的要带 `/v1`，有的要求完整接口地址。表单不容易看出当前字段属于哪一种。
- **对使用的影响：** 配置可能因为多填或少填路径而无法调用，用户只能靠试错。
- **建议改进：** 按模型能力说明需要填写“服务基础地址”还是“完整接口地址”，并提供对应服务商的示例；检测到路径重复时给出提示。
- **本次配置的参考填写：** LLM、语音识别和视觉模型使用 SiliconFlow 时，填 `https://api.siliconflow.cn/v1`；Embedding 字段使用完整地址 `https://api.siliconflow.cn/v1/embeddings`。其他服务商应以其接口要求为准。

### 4. 离开配置页会丢失未保存内容

- **我遇到什么：** 填写模型配置时误点了其他页面；返回后内容已经丢失，也没有离开提醒。
- **对使用的影响：** 需要重新填写，长配置尤其容易造成挫败感。
- **建议改进：** 表单内容发生变化后，离开页面或切换侧栏时提示“放弃未保存修改吗”；也应考虑刷新或关闭页面的提醒。
- **排查线索：** 当前未保存确认只覆盖表单内的返回按钮，侧栏导航没有检查配置是否已修改。

### 5. 模型配置导入 / 导出

- **我希望有：** 使用 JSON 文件快速导入或导出一套模型配置，减少重复填写。
- **建议改进：** 支持导出和导入服务地址、模型名、Embedding 维度及预算等字段。API Key 默认不导出明文；导入后可以重新填写密钥。
- **状态：** 这是功能建议，尚未验证实现方式。

### 6. 模型探测结果不明确

- **我遇到什么：** 点“拉模型”或“探测维度”后，主要通过短暂提示反馈；看不清是哪项能力、哪个模型正在检查，也不确定“模型列表能拉到”是否代表所选模型真的可以调用。
- **对使用的影响：** 配置失败时难以定位问题；提示消失后也不容易回看结果。
- **建议改进：** LLM、语音识别、Embedding 和视觉模型各自显示检查状态与模型名；区分“读取可用模型列表”和“实际调用当前所选模型”。检查中显示进度，成功后显示耗时（Embedding 还显示维度），失败后保留可读错误。修改相关配置后清除旧结果。
- **排查线索：** 当前前端 `ProfileForm` 的模型列表和维度检查以 toast 提示为主；现有检查不能覆盖四种能力的实际模型调用。后续实际探测应走服务端现有 AI 客户端和配额治理，不在浏览器或日志中暴露 API Key；测试可能产生少量供应商费用，应在操作前说明。保留 DEMO 账号只读限制，并尊重系统的减少动态效果设置。

### 7. 多个视频和长视频转写状态不透明

- **我做了什么：** 给三个视频分别点了“开始转写”。
- **我看到什么：** 看起来只有第一个视频的进度条在闪烁；其他视频是否排队、正在调用 ASR，或遇到第三方限流都不清楚。长视频也没有显示当前分片和已经转出的文字。
- **对使用的影响：** 无法区分“正常排队”“供应商限流后重试”“转写卡住”和“已经转完但后续仍在处理”，容易重复点击或误判失败。
- **建议改进：** 每个视频清楚显示排队 / 处理中 / 完成 / 失败、当前阶段、排队或运行时长、最近进度时间；长视频显示分片 `已完成 / 总数`、当前分片的时间范围、重试次数和已完成分片的文字。若发生第三方 429 或本地额度准入等待，明确显示原因、等待到期时间和下一次重试；任务长时间没有心跳时提示疑似停滞。还应在转写入口和排队状态旁说明当前服务配置允许的并发视频数及每个视频的 ASR 分片并发数，并标出该视频是在等待并发名额还是已开始调用；数值应从服务端配置 / 状态接口读取，避免前端写死。可先用轮询实现，不要求 ASR 服务提供精确百分比。工程上可新增 `GET /api/v1/media/task/:id/transcription-progress`，返回分片总数及各状态计数、当前分片 / 时间范围、重试和限流等待信息，并附上已完成分片文本；工作台和视频详情页只对处理中任务短间隔轮询，完成后停止。
- **本次运行核对（约 17:36）：** 数据库里任务 1、2、3 的 ASR job 均已完成，分别有 4、5、20 个成功分片；当前三个视频的整体阶段是 `indexing`，即 ASR 已完成，后续索引还在进行。Prometheus 当时记录 29 次 ASR 调用和 29 个分片均成功、provider in-flight 为 0，没有观察到 429 / failed / retry-wait 信号。因此这三条任务没有查到第三方限流证据；“只有一个进度条在动”不能据此判断另外两个没转写。
- **排查线索：** 当前 `config.yaml` 的 `transcribe_prefetch: 2` 允许一个服务进程最多并发处理两个转写任务；`asr_concurrency: 3` 限制单个视频内并行的分片调用，所以设计上不是一次只能转一个视频，第三个可能排队。ASR 对长音频按 300 秒窗口、5 秒 overlap 切分，并将分片的状态、重试次数和完成文字保存在 `video_transcription_chunks`。但前端工作台和视频库只在页面打开时拉一次列表；视频详情页虽然每 5 秒轮询任务状态，却只在完整转写完成后才拉时间线，用户看不到分片级进展和部分文本，也没有解释并发上限或排队原因。后端已有 `ai_call_logs` 的错误分类、ASR 分片指标及 provider retry 日志；供应商 429 会触发有上限的重试（当前配置最多 2 次，并遵循响应中的 `Retry-After`），但重试等待期间没有持久化、可供前端显示的当前状态。复核时曾看到队列 `2 ready / 1 unacknowledged`，稍后队列清空；该队列快照无法单独对应到具体视频。后续可以从 `internal/mq/consumer_transcribe.go`、`internal/mq/consumer_lifecycle.go`、`internal/ai/retry_policy.go`、`internal/model/transcription_chunk.go`、`internal/service/media_tasks.go`、`frontend/app/(main)/video/[id]/page.tsx` 和 `frontend/app/(main)/page.tsx` 接手。

### 8. 建立索引前没有说清用途与代价

- **我看到什么：** 视频转写后出现“建立索引”操作。现有确认框只说会按当前向量模型生成检索投影、不会重新转写、会消耗 Embedding 额度；没有直接说明索引能带来什么，因此不确定是否有必要建立。
- **它的用途：** 将已有转写文字分段并转换为向量，供语义检索和视频问答查找相关片段；只播放视频、看转写或摘要时暂时不需要。
- **副作用：** 会把转写片段发送给配置的向量模型服务进行处理，并消耗 Embedding 额度；不会重新转写，也不会改动原视频或转写文字。
- **建议改进：** 确认框同时说明好处、模型调用 / 额度消耗和数据处理范围，避免只展示技术术语。可采用文案：“建立语义检索索引？建立后，视频问答可以按内容含义找到相关的转写片段，并定位视频位置。系统会调用当前配置的向量模型处理已有转写文字并消耗 Embedding 额度；不会重新转写，也不会修改原视频或转写文本。”
- **状态：** 这是体验改进建议，本次仅记录文档，没有修改产品代码。

### 9. 画面证据应允许按视频选择

- **我希望有：** 画面证据作为可选能力。对于画面单调、主要依靠语音内容理解的视频，可以跳过抽帧和 OCR / 画面描述；需要识别课件、屏幕文字或场景时再打开。
- **对使用的影响：** 当前用户无法按视频决定是否需要这类分析，也看不出视觉处理的时间和价值。
- **建议改进：** 在上传后或视频处理操作中提供“生成画面证据”开关，并说明关闭后仍可转写和摘要，但不会生成画面 OCR / 描述。若需要支持处理后补做视觉分析，应有单独的“生成画面证据”操作和状态。
- **排查线索：** 当前 `VisualIndexConfig.Enabled` 默认开启，`cmd/server/wiring.go` 固定注册视觉索引器，`internal/mq/consumer_transcribe.go` 在转写任务开始时无条件启动视觉分支。设置页的视觉模型开关只决定是否调用外部 Vision API；即使没有启用视觉模型，本地 Tesseract 可用时仍会抽帧和识别 OCR。因此该开关不等同于“关闭画面证据”。

### 10. 画面证据预览显示重复帧

- **我看到什么：** 画面证据中多张缩略图看起来相同，但对应的 OCR / 画面描述随时间变化且内容合理。
- **对使用的影响：** 无法直观看出描述来自哪一帧，也不容易判断视觉识别是否准确。
- **建议改进：** 缩略图应使用该条证据对应的已保存关键帧；如果继续从视频播放源截取，应按证据时间跳转，等待 `seeked` / 视频帧就绪后再显示，并处理取帧失败状态。不要用不同时间戳对应同一张错误预览来暗示帧已成功加载。
- **排查线索：** 详情页 `renderVF()` 为每条证据传入自己的 `timeMs`，但 `frontend/components/VideoPoster.tsx` 的 `VideoStill` 把跳转时间限制为 `min(timeMs, duration * 0.2)`；超过视频前 20% 的所有预览都会落在同一时刻。这与“描述内容正确但缩略图重复”的现象吻合。后端会把关键帧对象保存到对象存储，并在时间线 `source_refs[].object_key` 中返回对象键；当前预览没有读取该对象键，而是重复加载整段播放源。进一步实现时需提供鉴权的关键帧预览地址，避免把内部对象键直接当公网 URL 使用。

### 11. 视频卡片的四段进度条缺少图例

- **我看到什么：** 每张视频卡片下方有四段不同颜色的进度条，但界面没有文字说明每一段的含义。
- **对使用的影响：** 不能仅凭颜色判断视频是在入库、转写、画面分析还是索引阶段，也不清楚每段的动画或颜色代表什么。
- **建议改进：** 在进度条旁增加紧凑图例或悬停提示，依次说明“入库 / 转写 / 画面分析 / 检索索引”；同时说明排队、进行中、完成和失败的视觉状态。给进度条提供可访问名称，不应将整个组件标记为 `aria-hidden`。
- **排查线索：** `frontend/lib/processBeats.ts` 固定返回 `ingest`、`asr`、`visual`、`index` 四段，按任务 `stage` 与 `has_transcription` 计算状态；`frontend/components/ProcessStrip.tsx` 仅渲染四个无文案的元素，并将容器设为 `aria-hidden="true"`。颜色规则位于 `frontend/app/globals.css` 的 `.proc-beat` 样式。

### 12. 索引按钮需要明确区分待建、构建中、已完成和需重建，并阻止重复构建

- **我看到什么：** 点击建立索引后，构建期间按钮仍显示“建立索引”；离开视频详情页再进入，按钮又能点，也无法判断之前发起的构建是否还在进行。已建立过的索引也需要明确显示“重建索引”，并在重建前再次确认。
- **对使用的影响：** 用户可能忘记是否已启动或重复触发索引，导致 Embedding 重复调用、额度消耗，多个构建还可能同时替换同一视频的向量数据。
- **建议改进：** 按索引 `status` 明确显示“建立索引 / 索引构建中… / 重建索引 / 索引失败，重试 / 需要重建”；`indexing` 时从服务端状态恢复按钮禁用和进度提示，不能只依赖当前详情页的 `busy` 内存状态。后端也应在同一用户、视频和 Embedding 模型上做原子占用 / 幂等防重，已经在构建时拒绝重复请求并返回现有状态。已有索引或版本需要重建时，确认框说明将替换当前索引以及会消耗 Embedding 额度。保留二次确认，并在确认框与按钮使用一致的动作名称。

### 16. 长视频的画面证据只覆盖前段

- **我看到什么：** 约 1 小时 36 分钟的视频，时间轴上画面 OCR / 描述色块只出现在前约 1 小时；后半段没有画面证据。

### 20. 根据视频内容自动生成推荐问题

- **想要的体验：** 用户打开视频详情或视频问答时，系统根据这段视频的转写、摘要和可用的画面证据，先给出几条值得询问的问题；点击问题即可直接发起问答。
- **对使用的影响：** 用户不必先自己组织问题，更容易发现视频中的关键主题、细节和可追问点，尤其适合长视频或刚接触内容的用户。
- **建议方案：** 使用低成本的小模型异步生成少量候选问题，问题必须能由当前视频内容回答，并尽可能关联时间戳或证据片段。结果按视频缓存，避免每次打开都重新调用；转写或索引尚未就绪时显示明确状态，内容更新后再刷新候选问题。可以提供“换一组”操作，并让推荐问题复用现有视频问答流程。
- **待评估：** 选择传给小模型的内容范围（摘要、分段转写或索引检索）、生成时机、刷新条件与调用预算；确认生成的问题不会超出视频证据，也不会把候选问题误显示成视频原文或模型已确认的结论。
