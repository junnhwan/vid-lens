本视频从 Kafka ISR（In-Sync Replicas）机制的设计动机讲起，系统梳理了 ISR 收缩与扩张的触发条件、replica.lag.time.max.ms 参数在 0.9→2.5 版本间的语义变化，以及 HW / LEO 两个水位线在副本同步中的推进逻辑。

后半段以一次真实的线上告警为案例：某分区 ISR 从 3 收缩到 1，排查过程涉及 follower fetch 线程瓶颈、日志刷盘抖动与 leader 切换风暴，最终定位为 broker 端 num.replica.fetchers 配置不足叠加磁盘 io-util 打满。视频给出了三条可落地的调优建议与对应的监控指标。

关键结论

  • ISR 判定在 0.9 之后只看时间维度，"偶尔追上的慢 follower"不会被踢出，是多数误解的根源。
  • num.replica.fetchers=1 是大流量分区副本滞后的最常见单点瓶颈。
  • ISR shrink 不等于丢数据，要结合 HW 是否回退判断真实影响面。

  1. #01

    今天我们聊一个在 Kafka 生产环境几乎一定会碰到的问题：ISR 为什么会收缩，以及它收缩之后你的副本到底还安不安全。

  2. #02

    先明确一个概念，ISR 不是"同步副本的集合"这么简单，它是 leader 认为"有资格在我挂掉之后接替我"的副本集合。判断标准在 0.9 之前是 lag 条数加时间，0.9 之后只剩时间，就是 replica.lag.time.max.ms 这一个参数。

  3. #03

    这个参数默认 10 秒，意思是 follower 只要在 10 秒内追上过 leader，就不会被踢出 ISR。注意它是"追上过"而不是"持续追上"，所以一个长期滞后但偶尔能抓一把的 follower 反而可能一直留在 ISR 里，这是很多人误解的点。

  4. #04

    接下来看一次真实告警。线上某个 topic 的分区 12，ISR 从 [1,2,3] 突然变成 [1]，监控上 ISR shrink rate 直接打满，但消息并没有丢。为什么？

  5. #05

    排查的第一步永远是看 follower 的 fetch 延迟。broker 2 和 3 的 replica fetcher 线程 backlog 持续增长，说明不是网络问题，是 fetch 吞吐本身跟不上了。

  6. #06

    到这里可以下结论了：num.replica.fetchers 默认只有 1，单线程 fetch 在大流量分区上就是瓶颈。把它调到 3，配合磁盘从 SATA 换 NVMe，ISR 抖动再也没有出现过。
