# Conversation execution timing (2026-09-27)

The assistant message's `retrieval_snapshot` is the display authority for a completed exchange. New Chat and Agent snapshots contain `execution_duration_ms` (nonnegative integer), `execution_started_at`, and `execution_finished_at` (UTC RFC3339Nano). Their `steps` array contains formal, server-authored execution steps. The same `execution_duration_ms` is returned in the Chat or Agent stream `done` event. Existing message IDs, answer text, citations, model/profile attribution, and Agent run IDs keep their meanings.

For ordinary Chat, the timer starts immediately before preparing the request context and stops after answer generation and citation finalization, before saving the exchange. It uses the server's monotonic elapsed time. Chat remains a Chat exchange; it does not create an AgentRun. For Agent, the timer starts at the durable run's creation and stops at the finalized answer before saving its exchange, including time spent awaiting resumed execution. These are distinct execution boundaries and are labeled **processing time** in the UI. While a stream is active, the browser may show **time waited** from local start; it switches to the server duration only on `done`.

The streaming `save` progress event is transient transport feedback. It is shown separately and is not a formal step in either live or saved `steps`. A completed run's formal steps and duration must match when loaded from the saved snapshot. Historic snapshots without a reliable duration display unknown; adjacent user/assistant message `created_at` values are database insertion times and must never be used to infer processing duration. Failed/cancelled streams without a saved answer keep their existing recovery semantics and do not claim a completed processing time. Provider reasoning and raw errors are not copied into these public fields.
