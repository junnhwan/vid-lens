# Study generation recipe v3

New requests freeze `study-v3`. Recovery keeps `study-v1` and `study-v2` prompt and checkpoint identities. The v2 contract remains in `study-generation-v2-contract.md`.

V3 gives each immutable source item an exact short alias (`e1`, `e2`, ...). Segment material and derived term hints use the same mapping. Before validation and checkpointing, the server restores every citation to its canonical manifest evidence ID. Unknown aliases are rejected. Stored sources, evidence identities, citations and revision lineage retain their existing format.

New requests freeze a UTC reference date in the policy snapshot. Segment prompts use that date and require source-only attribution: training memory cannot establish that a recently named product is unreleased, fictional or from the future. Recovery retains the frozen date, while earlier checkpoints without the optional date preserve their existing prompt digest. A narrow lexical guard rejects reproduced affirmative release/fiction/future-date judgments if the cited source lacks corresponding language, triggering the existing bounded repair with specific source-only instructions. Source assertions and negated judgments are allowed. This guard cannot establish semantic entailment or detect every paraphrase; final factual review remains necessary.

`source_context_revision=2` freezes a source-only reminder after the material messages. Older snapshots do not gain that message during recovery. Future-date and future-model cues require corresponding specific language; generic discussion of future technology does not authorize a claim about the material's date or model release status.

Input reservations and single-call context admission use a token estimate with message overhead and a 25% margin, rather than counting UTF-8 bytes as tokens. Reported provider usage replaces each estimate; reasoning tokens are recorded separately in call metrics and remain part of total completion usage. Configured total input/output/call/duration limits are retained.

Generation and organization calls mark their structured-output purpose. For known Qwen 3.5/3.6/3.7 hybrid model families, the compatible client sends `response_format=json_object` and `enable_thinking=false`. Other model requests retain their existing parameters. Server schema, hierarchy, citation and source checks still apply; JSON mode is not a substitute for validation.

V3 organization input contains numbered blocks, their titles/content and server-assigned merge keys. Only equally titled leaf blocks with the same type and original parent can share a nonzero key; sections, non-leaf blocks and opposing citations cannot be merged. Its output supplies member indices and a representative title index. The server checks total coverage, uniqueness, membership and merge keys, then reads canonical block IDs and titles from the original blocks. Schema-valid plans that collapse distinct concepts or chapters are rejected. Fact compatibility remains a model decision and requires human review.

After every source segment has been generated and validated, a structural, size, output-truncation or admission-budget failure during organization can preserve one group per original block. The saved version explicitly contains `organization_kept_segment_structure`; all original body content, hierarchy and citations are retained. This is not available for a missing/failed source segment, cancellation, expired context, lost lease or changed source. Final body validation and the existing fenced commit still run. A transport/provider failure that is not one of the enumerated recoverable cases remains a failure.

Run views include optional progress and budget diagnostics: last nonterminal stage, covered/total segments, call/input/output limits and the exhausted budget dimension. Existing terminal status fields remain compatible. Failed model calls persist only safe validation categories (`json_syntax`, `json_schema`, `citation_id`, `citation_validation`, `body_structure`, `source_attribution`, `organization_plan`), usage and elapsed duration, without prompt or reasoning text.

Implementation: `internal/service/artifact_generation.go`, `study_evidence.go`, `study_organization.go`; `internal/repository/artifact_steps.go`, `artifact_runs.go`; `internal/ai/chat_budget.go`, `chat.go`; `frontend/components/artifacts/RunDetail.tsx`.

Verification includes deterministic generation regressions, legacy v2 execution, exact alias mapping, rejection of unknown citations, organization fallback and cancellation. `TestArtifactRealSourceReplay` (build tag `real_llm`) reads an explicitly selected source run through a read-only production connection, copies its source material into an isolated fixture database, and uses the real selected model through the normal Submit/Execute/Commit path. It never updates the source user's records. The opt-in PostgreSQL fixture uses only `vidlens_artifact_test` with a disposable schema. Real outputs and diagnostics belong outside Git.
