# VidLens 升级实施规划

日期：2026-09-07。规划基线：main `f003dab73cb0946b6d551f005c17f7a0d1bbf89d`。

本文基于本轮源码审查和用户确认的升级方向，配合 [main 审查报告](vidlens-main-review.md) 使用。审查报告记录现状与验证证据；本文定义后续实施顺序、技术边界和验收方法。以下工作均为待实施计划，不代表功能已完成或效果已通过。

## 1. 目标与范围

本轮目标：让用户提出视频问题后，系统能够定位关键证据，在信息不足时有针对性地补看，独立核验结论，并提供完整原文和可回放画面。

两条工程主线：

- Agent / AI 应用：定位 → 观察 → 判断缺口 → 有限补看 → 独立核验 → 有证据的回答或明确不确定。
- 后端：并发任务、重复投递、进程崩溃和 Provider 故障下，任务状态与业务结果保持一致，计算复用可解释、可恢复。

本轮沿用现有 Go、PostgreSQL、RabbitMQ、Redis、对象存储及前端架构。优先扩展现有模块，不增加新的 Agent 模式或替换整套运行时。

### 1.1 已有基础

| 已有能力 | 本轮建设重点 |
| --- | --- |
| research 查询时取帧和 VLM 观察 | 修正状态、缓存与预算，增加按缺口调整的有限循环 |
| 独立 Inspector、反证搜索、像素核验 | 修正支持与冲突判定，避免无关候选导致过度拒答 |
| Evidence Ledger、引用、播放器和证据抽屉 | 保证原文连续、时间范围诚实、画面可核对 |
| ASR 分片并发、重叠窗口、文本拼接 | 建立结构化时间线和兼容降级路径 |
| MQ 任务租约、CAS、重试 | 修复并发错误通知，闭合消息去重与业务完成窗口 |
| 内容结果复用 | 区分计算所有权、模型版本和结果可见性 |

### 1.2 本轮暂缓

- 新增第四种或更多 Agent 模式。
- 跨视频 Claim Graph、多跳 Research Agent、Evidence Reel。
- MCP 接入、直播监控、完整视频编辑器。
- 引入 Kafka、Temporal 等替代现有任务链路。
- 大规模界面重做，以及与效果问题无关的通用抽象。

上述方向仅在当前闭环验收后，由真实需求或失败案例触发重新评估。

## 2. 实施顺序与依赖

| 阶段 | 内容 | 启动条件 | 完成门槛 |
| --- | --- | --- | --- |
| S0 | 修复已确认缺陷 | 可立即开始 | 针对性回归通过，主分支适用检查通过 |
| S1 | 建立真实效果基线 | 可与 S0 整理数据；正式基线在 S0 后冻结 | 数据版本、标注、配置、逐题结果可复核 |
| S2 | 按缺口主动补看 | S0、S1 完成 | 目标失败类别改善，拒答和成本边界受控 |
| S3 | 转写与引用连续性 | S1 提供边界失败样例 | 原文不被静默改写，引用完整，时间精度有依据 |
| S4 | MQ 与内容计算可靠性 | S0 后即可提前推进 | 故障注入和并发复用验收通过 |
| S5 | 综合验收与阶段收尾 | 本轮选定范围完成 | 可复现演示、评测报告、运行说明齐全 |

推荐顺序：S0 → S1 → S2 → S3 → S5；S4 在 S0 后尽早实施，其 MQ 去重修复不应等到所有视觉功能完成。偏后端建设时，可将 S4 排在 S2 前。

先完成每阶段最小切片并验收，再决定是否扩展。本文不要求一次实现所有可选项。

## 3. S0：修复结果可信度与执行可靠性缺陷

### S0-1：并发消费者错误通知

入口：[consumer_lifecycle.go](../../internal/mq/consumer_lifecycle.go)。

实施：

- 用同步的错误通知机制替换 worker 写、主循环无同步读的 `firstErr`。
- 首个 ACK/NACK 基础设施错误必须唤醒等待 delivery 或并发槽位的循环。
- 停止派发后取消本轮处理上下文，等待在途处理按截止时间结束，再关闭 reader 并交由外层重建。
- 明确 reader 关闭与在途 ACK 的顺序，避免关闭期间重复确认或失控派发。

验收：并发数大于 1 时，最后一条消息 ACK 失败、没有新 delivery，循环仍在测试限定时间内返回；NACK 失败同样覆盖；取消与通道关闭无 goroutine 泄漏；`-race` 无数据竞争。将本轮临时复现转成正式回归用例。

### S0-2：停止、切换会话与迟到响应隔离

入口：[useConversationSession.ts](../../frontend/components/chat/useConversationSession.ts)、[conversationSession.ts](../../frontend/components/chat/conversationSession.ts)、[api.ts](../../frontend/lib/api.ts)。

实施：

- 为 research / evidence_funnel 的 HTTP 请求传递 `AbortSignal`。
- 每次发送绑定请求标识和会话标识；事件、结果、异常及 `finally` 只允许更新所属请求。
- 停止、切换、新建会话、组件卸载使旧请求失效；不能仅依靠浏览器 abort 防止迟到结果。
- 同时检查历史消息加载的响应次序，避免较早的会话读取覆盖后来选择的会话。

验收：研究 A → 停止 → 新会话 B → 发送 B → A 迟到，B 的正文、引用、run ID 和 loading 均不变；旧请求 finally 不终止新请求；浏览器中重复执行停止、切换和快速发送。HTTP 取消不等于 Provider 已停止计费，后端须验证取消传播，无法取消的调用应记录实际边界。

### S0-3：Inspector 支持与冲突规则

入口：[evidence_inspector.go](../../internal/service/evidence_inspector.go)。

实施：

- 被正式引用的证据必须支持主张；缺失、伪造、越域及必要像素核验失败继续阻断。
- 未引用候选区分“无关”“相关但未确定”“真实反驳”，无关候选不因缺少支持而否决主张。
- 已确认反驳继续阻断；相关但无法核验的潜在冲突应返回不确定，不能简单全部忽略。
- 在像素核验前按 canonical source 去重，合并 cited 属性；同一来源不能重复占用同一主张的核验预算。

验收矩阵：支持字幕 + 无关图片可以通过；支持字幕 + 确认反驳图片阻断；被引用图片看不清不通过；来源伪造/越域阻断；同一证据在引用、检索和反证结果重复出现只核验一次。使用确定性测试固定聚合规则，并以真实图片检验语义效果。

### S0-4：视觉缓存状态与重试

入口：[visual_investigator.go](../../internal/service/visual_investigator.go)、[video_visual_observation.go](../../internal/repository/video_visual_observation.go)。

实施：

- 分开判断“帧文件可以复用”和“观察结果可以复用”。成功且版本一致的 observation 才可直接复用语义结果。
- `captured` 允许在有预算时继续观察；暂时失败记录原因、尝试次数与重试条件，不能永久命中失败。
- 核查唯一键和写入方法，使失败转成功可原子更新或产生可追溯的新尝试，不能只改读取条件却写不回结果。
- 缓存身份覆盖用户/视频作用域、内容版本、帧/裁剪参数、问题与必要事实、Provider/model 和观察协议版本；不得包含明文密钥。
- 并发重试使用所有权或 CAS，防止同一观察被重复付费执行。

验收：首次 VLM 超时后第二次成功；captured 在新预算下继续观察；同键并发请求不相互覆盖；成功命中不重复调用 VLM；模型/协议变化不复用旧语义结果；无法访问的旧媒体对象不能伪装成可回放成功。

### S0-5：调查状态与必要事实覆盖

入口：[visual_investigator.go](../../internal/service/visual_investigator.go)。

实施：

- `sufficient` 依据必要事实覆盖与决定性缺口，而非仅“调用未报错”。事实覆盖不能仅由模型自报 confidence 或字符串相似匹配认定。
- 模型输出解析失败、只返回“看不清”、缺乏证据绑定时保留 uncertain 和具体原因。
- 先判断目标是否达成：最后一次预算恰好取得全部必要证据可以 sufficient；预算耗尽且目标未达成才是 budget_exhausted。
- 预算不足、来源不可用、语义缺口分别记录。调查 sufficient 只是交给独立 Inspector 的候选，不是允许直接发布。

验收：空 facts、有决定性 gap、仅 captured、无必要证据均不能 sufficient；有效证据完整覆盖时可以 sufficient；预算用尽不丢失已有观察；重复缓存不能重置整次调查预算。

### S0-6：主分支平台检查

核实已有未提交 FFmpeg 路径修复的归属和适用性，保留 Windows 与 Unix 路径用例。业务审查不能把本地补丁通过写成 main 已通过。Docker 本地存储和端口变更另行处理，不混入 Agent 修复。

## 4. S1：真实视频效果基线

### 4.1 数据与标注

起步收集 30–50 个问题，覆盖下列类别；同一视频可有多个问题，但开发/封存集优先按视频或内容来源分组，避免同源内容泄漏。

| 类别 | 需要标注的关键内容 |
| --- | --- |
| 字幕可答 | 答案要点、原文、时间窗 |
| 仅画面可答 | 决定性帧、可观察事实 |
| 小字、PPT、表格 | 原始区域、应读出的内容 |
| 操作过程、短暂画面 | 顺序、前后帧、关键事件区间 |
| ASR 跨分片句子 | 人工参考转写、重复/漏句边界 |
| 声画冲突 | 两种来源各自内容、应如何回答 |
| 无证据问题 | 应拒答原因与不允许编造的结论 |

最小记录字段：case ID、视频内容哈希、问题、类别、答案要点、应否拒答、证据区间/帧/区域、标注者与标注版本。答案要点和决定性帧不进入待测 Agent 的提示或定位输入。

遵循 [评测目录约定](../eval/README.md)：规范和可公开样例放 `docs/eval/`，真实输入放 `docs-private/eval/`，结果放 `artifacts/`。使用现有评测入口和格式，先检查能否扩展，不并行创建另一套重复框架。

### 4.2 对照与指标

固定数据和 Provider/model，比较 A 仅字幕、B 字幕 + 离线视觉、C 在线取证。已有模式若同时改变了 Prompt、Inspector 或检索参数，应标记为整条产品路径对照，不能把差异全部归因于在线取帧；另设单变量消融验证单项收益。

| 指标 | 计算约定 |
| --- | --- |
| 任务成功率 | 满足答案要点、关键证据和拒答要求的题数 / 全部题数 |
| 错误拒答率 | 有充分证据却被拒答的题数 / 可回答题数 |
| 无支撑主张率 | 无可核对证据支持的事实主张数 / 生成事实主张数；零主张单独记录 |
| 时间定位 | 报告与标注区间的重叠、边界误差，保留未知时间比例 |
| ASR 边界错误 | 标注边界中的重复、遗漏、错误连接数量与样例 |
| 延迟与成本 | 端到端 P50/P95、失败/超时数、VLM 实际调用/重试/帧数、可获取的 token/费用 |

结果登记代码 SHA、数据/配置/Prompt 哈希、模型标识、缓存状态和逐题工具轨迹。缓存冷/热结果分开；费用无法获得时标记未知，不能按固定单价估算后当作实际账单。小样本 P95 仅作描述，不作为稳定生产指标。

### 4.3 验收门槛

正式比较前冻结标注、评分规则、目标类别和可接受预算。S1 先建立真实基线，不预填准确率或收益数字；S2/S3 的目标改善幅度应在封存集测试前，根据基线和使用要求登记，不能看完结果再改标准。人工抽检所有新增错误、拒答和声画冲突，不能只用同一个模型自评。

## 5. S2：按缺口主动补看

### 5.1 最小闭环

在现有 VisualInvestigator 内维护调查状态：目标、必要事实、已观察来源、未解决缺口、已执行动作、累计预算及停止原因。外层 Research Planner 提供目标和合法候选窗口；内部负责有限观察策略，避免内外层都无约束重试。

处理流程：候选定位 → 原图观察 → 形成事实与 gap → 选择一个受限动作 → 更新状态 → 达成目标或停止 → 交给 Inspector。

| gap | 允许动作 | 约束 |
| --- | --- | --- |
| 文字过小 | 原始分辨率 ROI 裁剪/放大 | 坐标基于实际帧尺寸；保留父帧、区域与变换参数 |
| 动作/状态变化不清楚 | 补前后连续帧 | 保留顺序与真实时间；静态单帧不能证明完整动作 |
| 时间窗口不匹配 | 更换候选或有限扩大窗口 | 仅当前视频、真实时长内；记录尝试过的范围 |
| 声画冲突 | 保留双方证据并核验 | 不静默选择一种模态覆盖另一种 |
| 来源/Provider 不可用 | 按策略重试或停止 | 不用反复取相同帧代替处理技术错误 |

先根据 S1 频率最高的失败类别实现一种动作，其余动作逐项增加。没有收益证据时不引入短 clip 推理或额外视觉向量索引。

### 5.2 执行约束

- 服务端绑定 user/task/source，Planner 不提供任意下载 URL、文件路径或跨视频 ID。
- 单次研究跨调查轮次累计帧、VLM 调用、重试、核验调用和 wall time；失败调用计入用量，命中缓存不虚记为新调用。
- 抽帧与观察分开缓存；相同动作无新增信息时停止重复执行。
- 参数校验覆盖时间边界、ROI、媒体大小；超时/取消传递到下载、FFmpeg 和 Provider。
- 观察结构必须能追溯到原图、区域、时间和版本；语义事实不是图片文件哈希本身能证明的。

前端在现有轨迹和证据抽屉显示“补看范围、观察结果、未解决问题”，不展示原始思维链。保持普通问答简单，research 承担调查能力，不复制新页面或模式。

验收：真实样例中至少完成一条由 gap 触发动作、取得新证据、改变最终结果的链路；无信息增益能停止；预算与取消测试通过；与 S1 固定路径比较目标类别收益和错误拒答；未核验内容不能直接进入正式发布结果。

## 6. S3：转写与引用连续性

### 6.1 S3-A：完整引用上下文

入口：[rag_evidence.go](../../internal/service/rag_evidence.go)、[EvidenceDrawer.tsx](../../frontend/components/chat/EvidenceDrawer.tsx)。

- 保留精确 anchor_quote；display_context 从同视频、同来源版本、同模态的相邻原文扩展到句子边界。
- 区分检索 child、生成上下文、引用 anchor 和阅读上下文；扩展阅读内容不自动成为主张支持证据。
- anchor 时间与 context 时间分别返回；只有可靠映射才能跳转，未知/粗粒度时间必须保留标记。
- 因上限截断时显式 truncated，不能把字符插值出的时间称为精确时间。

验收：长句跨 chunk、中文标点、英文段落、重复句、字幕/视觉混合索引均保持来源隔离；引用与上下文都是原始来源可查子串；抽屉能显示完整上下文并跳到正确视频区间。上限内无法补全时诚实显示截断。

### 6.2 S3-B：结构化转写时间线

入口：[audio_transcription.go](../../internal/ai/audio_transcription.go)、[strategy.go](../../internal/ai/strategy.go)、[consumer_transcribe.go](../../internal/mq/consumer_transcribe.go)、[stitcher.go](../../internal/transcript/stitcher.go)。

实施切片：

1. 定义转写结果契约：原文、segment 起止、可选 word 时间、语言、Provider/model、时间精度、处理版本和来源窗口。保持现有纯文本调用方可通过适配器工作。
2. 对确实支持结构化结果的 Provider 接入 segment/word 数据；不支持时使用 text-only 降级，不能生成虚假的词级时间。
3. 将 Provider 局部时间转换成视频时间，校验范围、顺序和缺失值；保留原始响应与规范化映射的版本关系。
4. 建立不可变 TranscriptAtom 或等价的统一片段模型；chunk、字幕和引用作为投影，不建立互相冲突的转写真相。
5. 按时间重叠与 core ownership 处理拼接；空窗口、非相邻窗口、重复短语和对齐失败保留原始证据及边界状态，不让 LLM 静默改写原文。
6. VAD、强制对齐仅在基线表明有必要时引入，并分别测收益与额外成本。

迁移采用新增字段/版本和兼容读取；不在启动时默认重算全部视频。选定少量任务显式重建投影，核对成功后再扩大范围；历史引用按其来源版本回放或标记失效，不能悄悄指向新文本。

验收：跨分片重复/遗漏样例有逐项对照；ASR 原文可追溯；时间精度不被夸大；历史 text-only 数据仍可阅读；索引更新不让旧引用错绑。仅句子展示变完整不等于 ASR 本身更准确。

## 7. S4：任务可靠性与内容计算协调

### 7.1 S4-A：派发版本与幂等完成状态

入口：[producer.go](../../internal/mq/producer.go)、[idempotency.go](../../internal/mq/idempotency.go)、[consumer_lifecycle.go](../../internal/mq/consumer_lifecycle.go)。

先画出现有 task/job/dispatch/processing token 的状态转换，确认现有 DB CAS 能承担哪些唯一性和恢复职责，再决定是否新增 Inbox 表，避免两套状态机竞争。

必须满足的契约：

- 同一派发 generation 的重投保持同一身份；显式重试/重算的新 generation 不被旧完成记录挡住。
- Redis 占位仅说明竞争所有权，不代表业务已完成。只有持久化完成或持久化交接成功才能将消息作为已处理 ACK。
- processing 具有 lease、owner 和 fencing/CAS；过期允许接管，旧 owner 不能覆盖新 owner 结果。
- 业务结果与完成标记尽量在同一数据库事务提交；涉及对象存储等外部副作用时使用稳定对象键、持久化意图和补偿/清理机制。
- DB 提交后消息投递的窗口由可证明的派发扫描或 Outbox 恢复；只有现有机制无法满足时再新增 Outbox。
- 兼容旧消息格式、已排队消息与 Redis 旧键，先部署兼容读取再切换新写入；不以清空队列作为升级方案。

故障矩阵：业务前崩溃、外部结果生成后崩溃、DB 提交后 ACK 前崩溃、重复/乱序投递、旧 generation 迟到、Redis 不可用、lease 过期接管。用真实测试中间件执行 kill/restart，记录最终状态、结果数量与恢复时长。允许模型调用在不可判定窗口重做，但不能称为 Exactly Once，也不能静默产生重复业务结果。

### 7.2 S4-B：内容计算协调

入口：[content_dedup.go](../../internal/service/content_dedup.go) 及对应任务创建、消费和结果仓储。

定义受限协调接口，返回 owner / waiting / reusable / failed 等结果；首次 cache miss 也必须争取计算所有权。

计算身份至少考虑：内容哈希、处理能力、Provider/model、语言、Prompt/处理版本及相关参数。身份不完整的历史结果保守处理，不默认跨配置复用。内容哈希升级不能误把客户端申报值当作服务端验证值。

计算复用与用户可见性分开：共享计算产物也必须为当前任务建立合法关联；跨用户复用需要显式权限和隔离策略，默认不得返回其他用户 task、引用或私有定制结果。完成产物发布后再唤醒等待者；失败/过期 owner 可接管；某个等待者取消不能错误取消仍被其他请求需要的工作。

验收：两个首次并发请求只有一个有效计算 owner；不同模型/语言/版本不错误复用；等待者可查询状态；owner 崩溃能恢复；结果引用属于当前合法 scope。成本节省按实际避免的调用及 usage 记录，不能把一次缓存命中直接等同于固定 token 或金额。

### 7.3 后续触发项：后台 Agent Run

当真实长研究因刷新、断网经常中断时，再实施独立 API/Worker 执行：提交 run 返回 ID、后台执行、取消与恢复、事件序号持久化、Last-Event-ID 回放。必须同时定义工具是否可重放、不可判定外部调用、重复发布以及取消后的产物处理；现有 checkpoint 或前端 SSE 不等于已满足这些契约。

## 9. 验证与交付记录

后端按改动范围运行定向测试及必要的 `-race`，S0 和综合验收运行全量 Go 测试。前端运行现有 test/typecheck/lint，涉及发布产物时补 build；交互问题必须有浏览器验收，不能只凭 reducer 测试收尾。

新增字段、缓存、索引投影和 Provider 协议需记录兼容策略及回退方式。实验能力可按配置逐项启用；回退不能绕过权限、来源验证或发布核验。数据库回退优先停用新路径并兼容读取，不直接破坏性删除已有数据。

## 10. 阶段性收尾标准

- S0 已确认缺陷全部闭环，未解决项不能以“已有测试通过”代替。
- 至少一组固定真实视频问题，有三条路径的逐题结果和失败归因。
- 至少一种 gap 驱动补看带来可解释收益；若无收益，记录结论并调整策略，不用新增工具掩盖失败。
- 上传、问答、证据展开、播放跳转、停止和切换会话可稳定演示。
- MQ 至少完成关键崩溃窗口的真实演练，恢复边界有记录。
- 文档能区分已实现、自动测试通过、真实效果通过及尚未支持的能力。

达到本轮选定范围的这些标准即可收尾。跨视频研究、后台完整运行时和其他可选方向不作为无限延期的理由。
