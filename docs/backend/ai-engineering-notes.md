# AI 工程问题与取舍

这里记录 VidLens 开发中值得复盘的模型调用、证据处理和可靠性问题，供后续维护和面试准备。重点是具体场景、为什么这样选、失败时怎么处理，以及这个选择牺牲了什么；接口和执行细节仍以[执行与恢复](execution.md)及源码为准。

首批记录于 2026-11-02，按源码基线 [`4fc1d58`](https://github.com/junnhwan/vid-lens/tree/4fc1d58a2eae8766179dbb0d8917d13130550cb0) 整理。它们是根据代码、提交和已有测试还原的设计复盘；测试场景不自动等于线上发生过的故障。下列测试是可追溯的覆盖点，本次整理没有重新运行，也没有据此证明真实模型的质量或成本收益。文件链接指向仓库当前版本，今后实现变化时应一起复核。

## 1. 长文输出不完整时，怎样避免整篇重来？

**问题。** 视频长文如果要求模型一次输出完整结构化结果，一次截断或 JSON 不完整就可能让整次结果不可用；反复要求重写整篇，也会把已完成内容重新放进不确定的生成过程。已有测试模拟了 `unexpected EOF` 和逐章修复场景，不能据此推断故障在线上发生的频率。

**选择与取舍。** 一次返回整篇的协议比较直接，但重试粒度太粗。当前文章循环把章节保存为带版本的持久化草稿：外层信封完整且满足提交约束时，分别校验章节，保留合法章节，并把被拒绝的部分及原因反馈给后续修复；整个 JSON 信封不完整时不猜测补全，而是保留此前已保存的正文、缩小后续单次工作范围，继续处理剩余来源。完成时仍要校验整体结构、引用与来源，再进入发布路径。

**代价与边界。** 增量保存增加了章节身份、版本冲突、重放和全篇一致性处理；草稿能恢复不等于文章已经发布，也不等于语义正确。它受原有调用、时间和无进展限制约束，不保证任意长视频都能成功。

**证据。** [文章循环](../../internal/investigator/article_loop.go)；[不完整 JSON 恢复测试](../../internal/investigator/article_delivery_test.go)中的 `TestDeliveryMalformedJSONRecoveryNarrowsWorkWithoutDroppingSavedDraft`；[局部写入与修复测试](../../internal/investigator/article_loop_recovery_test.go)中的 `TestArticleLoopPartialWriteRepairPreservesAcceptedChapter`。

**可以继续追问：** 一批里有合法章和非法章时，为什么能接受合法部分？如果连外层 JSON 都不完整，还能这样做吗？

## 2. 多模态取图如何避免挤占正文交付？

**问题。** 固定抽很多帧可能错过真正需要的局部画面，还会占用解码时间、图片输入和模型上下文；一味找图也可能耗尽完成正文所需的预算。单张静态帧本身不能证明连续动作或全片都没有其他画面。

**选择与取舍。** 当前文章交付策略让模型围绕章节提出具体视觉目标：先保存正文，再按需取附近真实帧，在后续写作中交付像素并保留时间来源。程序限制取图窗口、候选、微调和图片输入，并为剩余正文预留调用与时间；截图失败、可选配图格式错误或预算不足时，可以省略该图，继续处理正文。只给模型图片路径或占位描述不能替代实际像素。

**代价与边界。** 这个策略优先保证正文机会，可能漏掉有解释价值的画面；图片预算中的 token 为估算值，不是供应商实际计费。像素确实送达和引用可追溯，也不能证明模型的图注或对画面的理解一定正确。

**证据。** [按需视觉实现](../../internal/investigator/article_delivery_visual.go)及相关提交 `a60f6fb`；[视觉测试](../../internal/investigator/article_delivery_visual_test.go)中的 `TestDeliveryVisualSaveBeforeCaptureFailureStillPublishes`、`TestDeliveryVisualTimeRefinementIsActualAndDurablyBounded` 和 `TestDeliveryVisualBudgetReservesProseAndFinishIgnoresSearch`。其中微调测试使用合成视频，不能当作真实视频上的模型选图验收。

**可以继续追问：** 如果找图失败，哪些内容能省，哪些来源和正文校验仍不能省？为什么“发送过图片”不等于“看懂图片”？

## 3. 独立核验不可用时，问答怎样交付又不冒充通过？

**问题。** 模型已经生成有来源的回答，但独立核验可能超时、返回空结果，或者只支持其中一部分。等待所有核验完成才展示可能让用户长期看不到结果；把缺失的结论当成通过，又会把不确定内容包装成可靠结论。

**选择与取舍。** 结构和来源校验后，先向所属会话展示标明“核验中”的参考解读，它还不是最终回答。随后按独立核验结果区分 `passed`、`partial` 和 `unavailable`：部分通过时只把支持的内容放进已核验正文，其余列为未确认；没有可用结论时提供有来源的有限参考，并明确标记尚未核验。服务端创建回执，绑定最终内容、核验状态和来源身份，模型不能自行宣布通过。

**代价与边界。** 有来源的参考解读仍可能出错，用户需要看到状态与未确认项；`not_assessed` 既不是通过，也不自动等于矛盾。用户取消、执行权丢失、存储错误或整轮期限到期不能触发降级发布；单次核验调用超时与整轮任务失效要分开判断。

**证据。** [问答交付实现](../../internal/investigator/question_delivery.go)及相关提交 `796979b`；[问答交付集成测试](../../internal/investigator/question_delivery_integration_test.go)中的 `TestQuestionDeliveryPreviewAndFinalStates`，覆盖模拟的通过、空结果、部分支持、取消和期限等路径；[单元测试](../../internal/investigator/question_delivery_test.go)检查未核验正文不能被标成已核验。

**可以继续追问：** 为什么“审核模型没返回”与“审核发现反证”不能混为一谈？降级回答和最终确认之间靠什么绑定？

## 4. 模型请求已发出、结果未知时，恢复能保证什么？

**问题。** 模型请求发出后，进程可能在接收或持久化结果之前中断：服务端无法仅凭本地没有结果判断外部是否已经处理或计费。简单地把任务当作全新任务重跑，可能重复发送，也可能重置预算。

**选择与取舍。** 当前文章循环在发送前冻结本轮输入、工具和预算；操作账区分逻辑调用与实际发送，完成的本地操作可回放，接管时沿用已有状态与期限。未知发送也进入物理发送计数；是否继续由冻结的限制和对应错误路径决定。数据库围栏约束过期执行者的状态写入与发布。

**代价与边界。** 冻结输入、记录发送和恢复状态增加了存储与协议复杂度，而且保守计数可能提前耗尽预算。它约束的是本系统内的状态和发送次数，不能保证供应商侧恰好处理或计费一次；没有实际用量证据时，成本仍是未知。

**证据。** [文章循环与恢复](../../internal/investigator/article_loop.go)、[模型发送](../../internal/investigator/model_call.go)、[操作账](../../internal/store/artifacts.go)；[物理发送预算测试](../../internal/store/article_loop_test.go)中的 `TestArticleLoopPhysicalBudgetIsTransactional` 覆盖未知结果仍计入上限的场景。

**可以继续追问：** 数据库操作可以做到幂等，为什么外部调用仍可能重复计费？逻辑轮次和实际发送为什么要分开记？

## 后续如何记录

只收录有实际工程价值的问题：例如模型协议与证据边界、可靠性交付、成本与质量取舍，或有多种可行方案且最终选择会影响行为的场景。简单改名、样式调整和没有可靠依据的推测不必单独成篇。

新增时尽量写清：

1. **背景和具体问题：** 发生了什么，或明确标成什么风险；写明日期、适用版本，并链接可公开的复现、提交或测试。
2. **方案与决定：** 比较过什么、选择什么，解释触发条件、核心机制和失败时的兜底；不要把事后推测写成已确认的决策过程。
3. **验证与限制：** 区分静态检查、自动化测试、模拟服务、真实模型或真实视频验证；记录失败和未验证项，不编造质量、时延或成本数据。
4. **面试追问：** 留一两个能展开时序、权衡或边界的问题；个人参与和分工按实际情况说明。

文档只保留可公开的 Agent 实现与验证说明，不写凭据、私人运行数据或部署排障细节。实现变更后更新对应条目和源码证据，旧策略如需保留应标明版本。
