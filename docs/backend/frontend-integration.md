# Frontend integration

The visitor API is implemented under `/api/v1`; its routes and typed views are defined in `internal/httpapi` and `internal/domain`, with frontend types in `frontend/src/contract`. Optional focus, interpretation detail, model selection and portable exports follow the [product contracts](product-features.md). The active React application is in `frontend/`; `docs/prototype` is a separate static visual reference.

Serve the frontend and API through the same browser origin. The Vite development server proxies `/api` to `http://127.0.0.1:8086` by default and rewrites the upstream Origin to that backend origin; configure the development backend's `public_origin` accordingly. `VITE_BACKEND_ORIGIN` changes that target. A production proxy must preserve the external Origin and the backend's `public_origin` must match the public HTTPS origin. Preserve Cookie, CSRF and SSE headers and disable proxy buffering for SSE. No cross-origin CORS workflow is provided.

## Request flow

1. `POST /session` with `{}` and same-origin credentials. Retain `csrf_token`; the cookie is HttpOnly. This does not require a preexisting CSRF token.
2. `POST /requests` with `{video_url}` and optional model, purpose and detail fields, plus `X-CSRF-Token` and a newly generated `Idempotency-Key`. Persist `request.id` in the page URL. HTTP 201 means accepted, not completed.
3. Install the entire returned RequestView; subscribe to its stable `stream.url?after=<cursor>`. Prepare/generation run changes are server-owned.
4. Once `request.status=completed`, close SSE and GET `/requests/{id}/article`. Render typed blocks, citations and returned Frame URLs. The article is immutable. A held-open image/history view is local frontend state.
5. On first opening Q&A, ensure `/requests/{id}/conversation` or restore the selected owned conversation. Read turn history and use that conversation's accepted tail ID for `expected_last_turn_id`. Each new question/retry gets its own action key.

All mutating visitor requests require Origin and CSRF. Private resource reads require the anonymous cookie; public model catalogs and site statistics do not. A failed resource is still HTTP GET 200 with `failure`; Problems describe rejected HTTP operations. On 401, stop subscriptions and show session loss. Do not automatically create a new session and replay uncertain writes.

The optional generation spec, model catalog, export and external-reference additions are documented in [product features](product-features.md). Current clients send `X-VidLens-Contract: 2`; preserve `contract=2` in SSE URLs. `CLIENT_UPDATE_REQUIRED` ends automatic reconnects and requires a page upgrade before external citations can be consumed.

A dependency error while checking a cookie is 503, not evidence that the cookie expired. Keep the session and resource identity, then retry reads with bounded backoff. A known missing image returns unavailable metadata/null URLs after the failed content read; reading it does not start model or restoration work.

Request activity includes an optional `attempts` ledger with owned, deduplicated article runs, each attempt's saved/planned/inherited chapter counts, call/send counts and history URL. `total_model_calls` and `total_model_submissions` cover those retained attempts. This ledger does not alter the current SSE cursor or authorize another visitor's history. For full history, page the current URL and prior attempt URLs, deduplicate step IDs/shared source work, and preserve each run's ordering. The reading view and Q&A disclosures load all retained pages, with explicit loading/error/expiry feedback. A `model_submission` belongs under its `(run_id, model_call)` response row; it is not another logical call. Live activity upserts update plans and call/send counters as well as the visible title.

Follow the owned `request.retry_of_id` chain when loading complete request history as well: a source-preparation failure may have no article attempt yet. The UI bounds this traversal and reports incomplete/cyclic lineage explicitly. It does not splice ancestor events into the active request's SSE cursor.

Keep a network replay's original key/body, including when a response was lost. Read `Idempotency-Expires-At`; same-key replay returns HTTP 200 and `Idempotency-Replayed: true`. A deliberate retry creates a new request/turn with `retry_of_id`. Automatic retries keep the same identity. A completed article cannot be regenerated by the retry route.

Q&A retry uses the same synchronous write guard as sending. Only the latest retryable turn can be retried, with no active answer; disable its action until acceptance. Retain the retry key and expected history when the network outcome is unknown, clear prior errors on a fresh attempt, and refresh conversation history on `TURN_HISTORY_CHANGED` or `TURN_IN_PROGRESS`. Both visitor and example conversations apply these rules. Ignore responses from a departed workspace.

Successful single model submissions stay in the main activity row with elapsed time and usage. Show the nested send ledger only for multiple sends or a failed/unknown submission. Omit generic successful model receipt messages; actual tool activities, evidence frames and failure messages remain visible. Process history represents recorded actions and outcomes, not private model reasoning.

An active Q&A `model_response` step may include `model_progress`: `{state, observed_at, elapsed_ms, call_limit_ms}`. States are `waiting` (send admitted), `thinking` (actual reasoning activity received), or `responding` (actual content/tool-response activity received). The server emits the send/first-activity receipts immediately and subsequent receipts at most once every five seconds. These receipts contain no reasoning text, answer draft or provider payload; a thinking receipt does not approve an answer. They do not add model calls or submissions. `call_limit_ms` is clipped to the run's remaining execution deadline.

Show the current stage and wall-clock waiting time even when process details are collapsed. Anchor elapsed time and receipt freshness to server/receipt timestamps, advancing with a monotonic client clock. After 15 seconds without a new receipt, describe the last known activity and wait for further response rather than claiming fresh thinking. Keep cancellation available during model thinking and independent review. A pending stop is shown immediately and disables duplicate clicks; keep it visible through `cancel_requested` until the terminal snapshot. Ignore a stop response/error from another conversation or departed page, and preserve the next draft.

## SSE

The backend batches persistent-state polling per active resource. It emits `view.snapshot` for state/binding changes and can use `activity.upsert` for a consecutive step-only change. A current snapshot may skip covered increments, as permitted by v1; it always carries the current revision/run/seq. No answer tokens, drafts, Base64 images, raw model events or private reasoning are streamed.

Process control event types **before** cursor deduplication:

| Event | Action |
| --- | --- |
| `view.snapshot` | Install its entire RequestView/TurnView at the provided position |
| `activity.upsert` | Replace the full step by ID; require same revision/run and next seq |
| `stream.reset` | Close, GET the same resource, then create a fresh EventSource with its new cursor |
| `stream.auth_required` | Close and show lost session; do not replay writes |

After a run switch, install the higher-revision snapshot before increments. Ignore stale page-cycle callbacks, old revisions and duplicate sequence positions. A terminal snapshot may repeat its current cursor to confirm closure. EventSource `Last-Event-ID` takes priority over URL `after`; a no-ID reset/auth event can still inherit an old lastEventId. Heartbeat comments do not fire message callbacks.

On CLOSED/network errors, GET the resource and reconstruct a new EventSource with bounded backoff; CONNECTING should keep the existing native reconnect chain. Page departure only closes subscriptions, not work. Slow/over-limit subscriptions can close without canceling the task. Activities remain available via the resource's `/activity` endpoint until their separate history retention ends.

## Article, frames and Q&A

- The article's `mind_map` is a real tree: render parent/child relationships and non-navigable group nodes, not a flattened section list. Leaf `section_id` links navigate to published chapters. Use article sections for an independent side outline and current-reading highlight; published older maps keep their original structure.
- Q&A distinguishes the user's question from the assistant's answer. Optional `answer.parts` are `{title, block_ids}` groups with titles chosen for the actual question, not a fixed answer template. Render each canonical block once, retain blocks outside groups, and keep existing answers without parts readable. The process disclosure is separate from the answer; send records stay inside logical-call details.
- Sending immediately moves the question into a separate pending bubble and clears the composer. This transport state is not a server turn or a model execution. Reuse the loaded conversation and share in-flight history loads; a synchronous guard prevents double sends. Preserve idempotency keys for uncertain writes, retain a failed question for editing, and do not overwrite a newer draft when the response arrives.
- New answers may include server-owned `evidence: {text_sources: [{citation_id, text}], viewed_frame_ids: [], review: "passed"}`. Text is copied from the saved original segments; timestamps still come from their canonical citations. Viewed frame IDs come from successful author model inputs containing real pixels, not captions, planned tools or reviewer-only images. Render these sources in an expandable panel. Missing evidence on older answers means unknown, not zero images. Discrete citation clusters show a first timestamp and count rather than an artificial continuous range.
- Render blocks and inline types structurally. Never interpret model text as HTML. `background_explanation` is visibly distinguished from video content. Unknown types need an explicit compatibility state.
- Use section/block IDs for anchors and passage selection. v1 accepts one frame together with either the legacy `context.passage` or an ordered `context.passages` array of `{section_id, block_id, quote}` objects. Multi-block selections may cross chapters and must form one continuous range: the first quote is a block suffix, intermediate quotes cover complete blocks, and the final quote is a block prefix. Every quote is checked against the immutable article. The existing selection character limit applies to the whole selection after Unicode whitespace normalization, including one separator between blocks; duplicate, reordered, skipped or mismatched blocks and mixed single/multi forms are rejected. Existing single-block requests and history remain compatible.
- Use Frame `time_ms` for display/citations and preserve figure sequence order. `requested_time_ms` is acquisition intent. Expired/unavailable frames have null URLs. Image GETs never download video or call models.
- Chapter starter questions additionally send optional `context.section_id`. The server checks that it belongs to the conversation's immutable article; it is part of the idempotency body and cannot select another article. No fabricated selection quote is needed.
- A new materialization has a new ID, optionally `replaces_frame_id`; it does not rewrite a published article. A failed image read should refresh Frame metadata.
- A visual question may enter `waiting_dependency` while the server restores the same original source once. Keep the same turn subscription. Restore steps appear in that answer's history; do not subscribe to an internal restore run.
- `answer` is null until committed. Only the current private conversation is used; prior generated answers are context, not original evidence. Canceled/failed drafts are not answers.
- Stop generation ends that request's demand and freezes its history. Another visitor's shared work can continue. Stop Q&A waits for a fenced canceled terminal state before the next turn.

## Minimal desktop acceptance

Check initial session creation, create/replay/conflict, refresh during preparation, switch to generation, actual frame display/zoom, immutable article reading, frame/passage questions, double-tab turn conflict, cancel/retry, SSE reconnect/reset, expired image behavior and media restoration. Preserve the reader's scroll/focus while status changes. The product targets desktop Web.

## Multiple conversations within one video

`GET /api/v1/requests/{request}/conversations` lists only the current visitor's conversations for that reading record. Items retain the conversation metadata and add `title` (the first available question, capped at 48 characters), `updated_at` and `turn_count`. `has_more` / `next_before` paginate in stable creation order; pass the owned cursor as `before`. `POST` to the same URL with `{}` and a fresh idempotency key creates an empty thread. A network replay retains that action key; successful replay returns the original conversation and starts no question or model work. `GET /api/v1/conversations/{conversation}` refreshes the selected thread metadata. The existing singular ensure route opens the newest thread for compatible clients.

Persist the selected identity per video in the visitor's local store, validate it against the current request/article, and recover an inaccessible selection through the owned video endpoint. Thread activation stops the previous client stream, restores that thread's in-page composer draft and reads its turns; it never cancels server work. Stale snapshots, activity and history reads cannot replace the newly selected thread. Preserve uncertain question writes and use separate idempotent creation slots. History titles and messages must be rendered as text. No other visitor's conversation metadata is returned.

Model history remains `PriorTurns` from the same conversation only. Example conversations share the per-example question allowance across threads. Original-source validation, per-thread ordering, active-turn exclusion and existing server admission limits continue to apply.
