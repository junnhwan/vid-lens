## 0. 三条铁律（先记这个）

1. **三段式回答**：痛点 → 选型（为什么是它）→ 效果（有证据的数字）。任何技术名词都只站在选型理由后面，不许堆名词。
2. **MRR 数字必须带口径**（最容易翻车，见下）。
3. **三不说**：
   - 不说 "model rerank 一定提升检索质量"——更多候选池下它反而降过 MRR。
   - 不说 "答案准确率提升"——没有任何评测证据。
   - 不主动说 BM25 全开——生产是关的，部分评测里它是负优化。

### MRR 数字答疑卡（被追问就用这张表）

| 问题 | 答案 |
|---|---|
| 0.78 和 0.93 是什么口径？ | 2026-07-19 本地评测的**困难问题集**：原 45 条里筛 `semantic`+`detail` 共 30 条。0.778→0.933 四舍五入得 0.78→0.93。证据：`docs/eval/2026-07-19-rag-evaluation-session-record.md` §3.6 |
| 全量 45 条是多少？ | baseline 0.841 → 优化（Rewrite+多查询+rerank）0.930，Hit@1 75.56%→88.89%（+13.33pp）。同上记录 §3.5 |
| 评测集是什么性质？ | 本地 15 个视频、45 条**人工标注**问题，每条绑定精确 `target_vector_id` 作为命中标准；dev 集，**不是** sealed test，**不是**线上生产指标 |
| 结果显著吗？ | 按 15 个 source group 做 20,000 次 cluster bootstrap：Hit@1 delta 95%CI [-2.22, 24.44]pp，MRR [-0.007, 0.137]，**区间覆盖 0——不能宣称显著或线上收益**，只能说"本地评测提升" |
| 为什么不是全量数字？ | keyword_exact 类 15 条基线本来就好（纯向量就几乎全中），算进平均会稀释"Query Rewrite 解决模糊/细节问题"的故事；挑出难集更能说明优化价值，同时也解释了选型动机 |

> 如果面试官很懂，追问 "但后来 strict 框架里 model rerank 和 deterministic 结果相同，legacy 50-case 里 model rerank 反而降 MRR，你怎么看"——
> 答：**不同候选池规模结论不同**。单视频/小候选池里 rerank 就是把遗漏片段排回第一位的"位置修正"，模型不模型无所谓（strict 6-case 里两者逐位相等）；大混合候选池里 model rerank 若丢弃 RRF 痕迹纯按模型重排，容易打乱本就对的顺序（50-case 里 MRR 0.823→0.638）。所以线上默认 deterministic rerank、model rerank 只在显式配置下启用——这个决定正是评测驱动出来的。能说出这句 = 面试加分项。

## 1. 一句话 + 30 秒自我介绍

**一句话**：映知是一个 AI 长视频理解与问答平台——用户上传或粘贴链接后，后端异步完成 ASR 转写、大模型摘要和基于转写的 RAG 索引，之后用户可以对视频内容提问，回答带可点击的引用片段。

**30 秒稿（背熟）**：

> 我做的是一个 AI 长视频理解与智能问答平台。核心痛点是：长视频处理链路又长又容易失败——转写动辄几十分钟、外部 ASR 服务还不稳定。所以我把链路拆成三段异步任务：分段转写、大模型摘要、RAG 索引，用 Kafka 解耦，配了任务状态机和阶梯退避重试。转写这环我按 300 秒分片，每片单独持久化，失败只重跑失败的片，不回放整个视频。检索侧，用户的问题经常表述模糊，单一路向量召回覆盖不够，所以我做了 Query Rewrite、多查询召回和 Rerank 的多阶段检索，在自建的困难问题集上 MRR@5 从 0.78 提到 0.93，并且回答会带上引用片段，可追溯到具体是哪段视频内容支撑的。

> 注：只提 ASR / 摘要 / RAG 索引这三段。**不要主动展开 download/yt-dlp**——它是外部依赖重的一条可选的接入路径，不是架构亮点，被问到了再一句带过。

## 2. 90 秒整体架构（"从头讲讲这个项目"）

> 用箭头讲因果，不要念名词。

1. **上传**：直传 / 分片上传断点续传 / URL 下载。分片走 Redis 记已传片号，最后 MinIO 服务端合并。
2. **可靠投递**：上传成功后把任务落 PostgreSQL 落库，再投 Kafka。任务有一个六态状态机（Pending→Queued→Running→Completed/Failed/Dead），消费端拿到 processing lease 才干活，处理成功后手动提交位移。
3. **转写（主亮点）**：消费 `video-transcribe` → FFmpeg 按 300s 切片 → 每片调外部 ASR、结果独立落库（片级 pending/running/completed/failed）→ 失败只重跑缺失片。
4. **摘要（次亮点）**：复用转写结果，消费 `video-analyze`，LLM 生成结构化摘要。
5. **RAG 索引**：消费 `video-rag-index`，把转写文本分块 → embedding → 写入 pgvector，`video_chunks` 是事实源、向量是可重建投影。
6. **问答**：`strict_rag` 模式下走 Query Rewrite → 多查询向量召回 → Rerank → 组装带引用（`[C1]` token）的 prompt → LLM 生成；没有索引就 fail closed，不瞎编。

```
上传/URL ──> task(PostgreSQL 六态机) ──> Kafka
   video-transcribe ──> FFmpeg 300s 分片 ──> ASR 逐片持久化 ──> transcription 行
   video-analyze   ──> LLM 摘要（复用转写）
   video-rag-index ──> chunk → embed → pgvector（video_chunks 为事实源）
Q ──> QueryRewrite ──> 多路向量召回 ──> Rerank ──> LLM+[Cx] 引用 ──> 带引用回答
```

### 3.1 分片上传与断点续传

> 简历：采用分片上传与断点续传机制，通过 Redis 记录分片状态并使用 MinIO 服务端合并，避免上传中断后整文件重传。

#### 3.1.1 故事稿（30s，能直接说）

> 大视频动辄几百 MB，弱网下一次整传很容易中断，中断就得从头再来。我把文件切成 5MB 左右的分片：**每片先实打实落到 MinIO，再把片号写进 Redis**；再次上传时前端先查 `check-upload`，服务端把已传的片号列表返回，前端只补传缺失的那几片。全部到齐后 `merge-chunks`，用 MinIO 服务端 copy 在对象存储内部把分片合并成一个对象——客户端和服务器都不用把整个文件再搬一遍。合并时校验分片大小和总大小，对不上就拒绝，防止"中途换了个文件"拼出脏数据。

#### 3.1.2 概念地基（"人话"表）

| 概念 | 人话 |
|---|---|
| 分片上传 | 把一个大文件切成 N 块分别上传，再合并 |
| 断点续传 | 中断后再次上传时，**只补缺失的块**，不重传整个文件 |
| 服务端合并（compose） | 对象存储在自己的存储空间内把 N 个对象拼成一个新对象（S3 的 Multipart Upload 思路），**数据不经过应用服务器** |
| Redis Set | 记录"哪些片号已上传完成"的集合，天然支持查缺失/查重复 |
| 会话规格（manifest） | 这次上传的 file_size / chunk_size / total_chunks 三个关键参数，服务端存一份，用于判断是否"同一个文件" |
| 先落盘、后标记 | 一致性原则：状态集合必须永远等于"真实已存在的分片" |
| file_md5 | 分片的"会话钥匙"，标识文件、跨请求关联同一批分片 |

#### 3.1.3 痛点 → 方案

| 痛点 | 方案 | 解决的机制 |
|---|---|---|
| 大文件弱网整传易失败，重传成本高 | 分片 + 断点续传 | 失败局部化到"某一两片"，补传缺失片即可 |
| 传了一半换个文件 / 规格改过，残片拼出脏文件 | 会话规格校验 + 不匹配自动重置 | 换文件时清掉旧状态重来，而不是傻乎乎接着传 |
| 合并时没拿锁，两个并发请求把分片拼两次 | Redis 锁按 md5 互斥 | 后到者体检"已有资产"直接复用 |
| 合并结果文件损坏没人发现 | 合并后 size == 期望 file_size 校验 | 对不上删除产物并报错 |

#### 3.1.4 逐环节拆解（项目实际实现）

| 环节 | 发生了什么 | 为什么这么设计 |
|---|---|---|
| check-upload | 前端带上 file_size/chunk_size/total 来查进度：服务端先校验"规格"是否和 Redis 里存的一致，不一致就**清掉旧状态+删掉旧分片**重来；一致则返回已传片号列表 | 规格是"同一个上传会话"的身份证明。防的是：上次停了，这个用户又选了另一个文件，但片号还能对上 0~9 —— 必须让"文件变了"这件事重置 |
| upload-chunk | ①分片字节先 `UploadFile` 到 MinIO `chunks/{md5}/{n}`；②成功后 `SAdd` 进 Redis Set；**若这步失败就把刚落的对象删掉回滚** | 保证"Set 里的片号 = 一定已落盘"。若反过来先标记再落盘，标记了却没数据 = 假进度，合并时必炸 |
| 状态 TTL | Redis 上传状态 24h 过期 | 是一次性的临时状态，不上 DB；24h 内没传完就让用户重来 |
| merge-chunks | 拿 Redis 锁（按 md5）→ 逐个校验所有片号都在 Set 里 → MinIO `ComposeObject` 服务端合并 → size 校验 → 建资产、置 COMPLETED、清理分片和状态 | 锁防并发拼两次；逐片校验防"缺片还硬拼"；size 校验是最后一道完整性保险 |
| 已完成资产复用 | merge 前先 `FindByMD5`：**同一文件的已有资产直接复用，不重传不重拼** | 内容去重：同一视频第二个用户秒建任务（代码事实，简历外亮点，见 §6） |

**为什么"先落盘、后标记"值得展开讲**：这是这道题里最显功力的一行。面试官问"怎么保证状态不骗人"，你答"我们的约定是：**只有真实落在对象存储里的分片才会进 Redis 集合；Redis 集合的大小必须永远等于真实分片数**。哪怕 Redis 临时写失败，我们把刚写的对象删掉回滚，也不留'假完成'"。这条把「状态是代理、落盘才是事实」的一致性观讲清楚了。

#### 3.1.5 可靠性细节汇总

- 24h TTL：断点续传窗口内有效，过期状态自动回收。
- 规格重置：文件换了，旧分片物理删除 + 状态清空（`resetChunkUpload` 逐个 `DeleteObject`）。
- 并发合并互斥：Redis 锁 + 锁冲突时复查资产实现幂等（两个请求谁先合成都行，后到者复用结果）。
- 最终完整性：每片 size 严格 = chunk_size；`ComposeObject` 返回 size 必须 == file_size，否则删产物报错。

#### 3.1.6 追问演练

- Q：中断后怎么续传？→ `check-upload` 返回已传片号集合，前端只补缺失片；24h 内有效。
- Q：Redis 丢了呢？→ 状态是**可重建**的临时数据，MinIO 里的分片还在；重查进度只是丢了"进度"没丢数据。
- Q：有没有逐片哈希校验？→ 诚实：目前是**大小 + 合并总大小**校验，没有逐片 SHA-256；这可以做成 upload-chunk 的可选字段，是明确改进点。别吹。
- Q：为什么用 Redis 不用数据库？→ 高频、短生命周期、Set 语义（查缺失）恰好匹配；真正的资产事实在 MinIO + PostgreSQL 的 asset 表，Redis 只当进度代理。
- Q：前端为什么还要问我？→ 前端调用方式不是重点，重点是服务端保证了"幂等 + 可查询"。

#### 3.1.7 边界（别踩）
- 简历只写"Redis 记分片 + MinIO 服务端合并"，**没写**逐片 SHA-256，别补吹。
- 没有"断点续传成功率提升 X%"这类量化，别编。
- 别把"跨用户去重复用"当作简历主叙事（§6 里是可选弹药）。

### 3.2 Kafka 异步调度 + 状态机 + 阶梯退避重试

> 简历：引入 Kafka 异步调度 ASR、摘要生成和 RAG 索引等长耗时任务，结合任务状态与阶梯退避重试，实现阶段追踪和异常恢复。

#### 3.2.1 故事稿（30s，能直接说）

> ASR、摘要、索引每个都是分钟级、还依赖外部 AI 服务，同步做在 HTTP 请求里用户根本等不起。所以我把它们拆成独立消费者：上传完成只**落库 + 投递**，立刻返回。任务在 PostgreSQL 里有**六态状态机**（Pending→Queued→Running→Completed/Failed/Dead），前端轮询就能看到走到哪。失败不直接死，按 **1 分钟 → 5 分钟 → 15 分钟**阶梯退避重投；重试到头仍失败就进 Dead，用户可重新触发，不静默丢。

#### 3.2.2 概念地基（"人话"表）

| 概念 | 人话 |
|---|---|
| 异步任务 / 消息队列 | HTTP 请求只负责"接受任务、立即返回"，真正耗时的活在后台进程做；两部分靠消息传递解耦 |
| Kafka | 持久化的消息管道：消息落磁盘，消费方挂了消息不丢，可被另一个消费者接手 |
| topic / consumer | 一类任务一个主题（video-transcribe / video-analyze / video-rag-index），每个主题一个消费者 |
| 位移（offset） | 消费者在主题里的"读到哪了"指针；手动提交 = 处理成功才更新指针 |
| 六态状态机 | Pending（建了任务）→ Queued（已投队列）→ Running（消费者在跑）→ Completed / Failed / Dead（重试耗尽） |
| processing lease | "这个任务现在我承包了"的执行租约：token + 版本 + 过期时间，谁抢到谁干活 |
| 阶梯退避 | 重试间隔随时间扩大（60s/300s/900s），给外部服务恢复时间 |
| 幂等（idempotency） | 同一个任务/消息被处理两次，结果也只有一次生效 |

#### 3.2.3 痛点 → 方案

| 痛点 | 方案 | 为什么能解决 |
|---|---|---|
| ASR/摘要/索引是分钟级耗时，同步请求等不起 | 拆 Kafka 消费者，请求即回 | 用户立刻拿到"已受理"，耗时转后台 |
| 上传是 API 进程、转写是消费者进程，两边要跨进程可靠交接 | Kafka 持久化消息 | 消息落盘，两边进程互不依赖，消费者挂了消息还在 |
| 外部 AI 服务不稳定（超时/限流/5xx），需要按节奏重试 | 阶梯退避 + 错误分级 | 1→5→15 分钟给服务恢复窗口；不可重试的错误不浪费重试 |
| 多个消费者可能抢同一任务，重复处理浪费+结果错 | processing lease | 谁拿到租约谁干，其它消费者跳过；崩溃后租约过期可重试 |
| 消费方崩溃/处理一半，任务没人知道 | 状态机落 PostgreSQL + RetryScheduler 补投 | 状态是持久事实，可扫描、可补投、可对外展示 |

#### 3.2.4 逐环节拆解（为什么是这套设计）

**① 为什么用 Kafka，而不是 goroutine / 定时任务 / 直接同步调用？**
- goroutine 池：进程一挂全没了，没有持久化，跨不了进程。这是最核心的否决点——转写有时几十分钟，进程重启就要能恢复。
- 定时扫描 DB：常驻轮询有延迟、打 DB，且是"拉"模型；Kafka 是"推 + 可积压"，语义更贴"事件驱动"。
- 同步 HTTP 调用：用户等几分钟，前端超时，不可接受。
- **结论话术**："我要的是跨进程 + 持久 + 可重试的可靠传递，这是消息队列的定位；Kafka 给了我落盘保证和消费进度管理。"

**② 为什么状态放 PostgreSQL，不只靠消息？**
- 消息是一次性事件，状态是持久事实。前端要查进度、运维要审计、消费者要判断"这任务做到哪了"，都得靠可查询的 DB。
- 反过来说：Kafka 消息丢了/重复了，状态机 + 幂等能兜底；**消息只是触发器，任务有没有做对，由 DB 状态裁决**。这句话是本节的灵魂，面试官很吃。

**③ processing lease 是什么、为什么要？**
- 场景：Kafka 是"至少一次"投递，两个消费者可能同时拿到同一任务消息；转写跑 30 分钟，绝不能两个一起跑。
- 设计：消费者干活前先到 DB 用 `task_id` 拿租约（token + 版本 + 过期，DB CAS 判 busy/stale/terminal/acquired），拿到才干活，处理中**心跳续约**（默认 30 分钟租期）；进程崩溃 → 心跳停 → 租约 stale → 别的人可接管。
- 关键区别：这不是"Redis 互斥锁"那种普通锁，是带**所有权 + 过期 + 续约**的执行租赁，直接支撑"长任务崩溃恢复"。

**④ 为什么手动提交位移？**
- 自动 commit 在"拿到消息"时就更新指针：若处理到一半崩溃，重启后这消息不会再给任何人 → **处理端丢任务**。
- 手动 commit = **处理成功才提交**：要么成功提交、要么触发重试，没有"既没成功又不重试"的洞。这正是简历"异常恢复"没明说但最硬的一层。

**⑤ 为什么要幂等/去重？**
- 就算手动 commit，重试/重复投递仍可能带来重复消息（Kafka 至少一次语义）。所以消费前先查任务/结果状态（`internal/mq/idempotency.go`）：已成功就跳过，不重复生成摘要/索引。

**⑥ 为什么阶梯退避 60/300/900 而不是固定间隔？**
- 外部 provider 的 5xx/限流往往要等它自己恢复，固定短间隔=在风头上反复撞，浪费也加剧对方压力。
- 1→5→15 分钟既给恢复窗口，又不至于把几天才恢复的任务拖到用户无感；上限封顶，超了进 Dead 由用户决定。

**⑦ 错误分级**：`isRetryableError` 把错误分两种——可重试（timeout/网络/429/5xx/provider）和不值得重试（没配 AI 服务、文件不存在、解密失败、视频 unavailable）。后者"早死早提示"，不消费重试额度，也避免了"永远救不回来还一直刷"的死循环。

**⑧ 三层可靠性栈（贯穿 3.2 与 3.3 的亮点，主动讲）**：
```
第 1 层 投递可靠：任务状态落 DB + 成功才 commit + RetryScheduler 补投
第 2 层 处理可靠：processing lease 保证同一任务仅一个消费者执行
第 3 层 粒级可靠：ASR 内部按片持久化，失败只重跑缺失片（见 3.3）
```
话术："同一个'失败可恢复'的思路，我做了三层：从消息投递，到任务执行，再到任务内部的片段。"——能把失败恢复讲出层次感的候选人不多。

#### 3.2.5 追问演练

- Q：重试几次？间隔多少？→ 默认 3 次：60s / 300s / 900s；provider 若返回更长的 Retry-After，按其值。
- Q：消息会不会丢？→ 三层：①任务状态在 PostgreSQL（消息只是触发）；②处理成功才手动 commit；③过期任务由 RetryScheduler 按状态扫描补投。**诚实边界**：DB 提交后、Kafka 投递前这个极窄窗口，目前靠扫描补投兜底，后续计划引入 transactional outbox——能说出"已知边界 + 演进方向"本身就很加分。
- Q：重复消费会不会出问题？→ 消费前查状态、幂等去重、DB 状态 CAS，保证同一任务只执行一次业务动作。
- Q：为什么状态在 DB 不在 Redis？→ 要可查、要审计、要跨服务共享，DB 是事实源；Redis 只放短期高频状态（分片、限流、锁）。
- Q：消费者做到一半崩了？→ lease 过期/stale 释放，其它消费者接管；已完成的转写片复用不重跑（串 3.3）。

#### 3.2.6 边界（别踩）
- 简历没写 outbox / "绝对不丢消息"，别吹到那个程度。
- 三层可靠性是"恢复可靠"，不是"高可用/容灾某某九"——没有压测支撑的数字别编。

### 3.3 长视频分段 ASR + 失败片段复用

> 简历：设计长视频分段 ASR 与结果持久化机制，任务异常后仅重跑失败片段并复用已完成结果，避免整段视频重复处理。

#### 3.3.1 故事稿（30s，能直接说）

> 转写是整条链路最不稳的一环。外部 ASR 单次请求体有 ~10MB **硬限制**，长音频根本传不进去；就算传得进去，转写到第 30 分钟挂掉，整体重来等于前面全白做。所以我把音频先用 FFmpeg 按 **300 秒**切成一段段，**每一片单独调 ASR、单独落库**（片级 pending/running/completed/failed + 每片文本）。某一片失败，重试只重跑那一片，已完成的片直接复用拼接——失败恢复的成本只跟失败片数相关，而不是整个视频。这个思路跟消息投递、任务租约是同一条线，只是粒度更细：**从投递可靠、处理可靠，一路做到"任务内部片段可靠"**。

#### 3.3.2 概念地基（"人话"表）

| 概念 | 人话 |
|---|---|
| ASR | 把音频转成文字（转写）。外部云服务，有请求体大小/时长上限 |
| 硬约束 vs 优化 | 分片在这里**不是优化**，是 ASR 单次调用 ≤10MB 逼出来的硬前提（代码注释明确写了 hard requirement） |
| 片级状态机 | 每个转写片段单独一个状态行（pending/running/completed/failed），而不是整个任务一个状态 |
| 失败复用 / 断点续跑 | 已完成片段的结果落在数据库，重试时跳过、只跑缺失片段 |
| 隐性故障 | "表面成功、内容被截断"——请求过大被服务端截断，状态是成功的但文本不完整 |

#### 3.3.3 痛点 → 方案

| 痛点 | 方案 |
|---|---|
| ASR 单次调用 ≤10MB / 时长上限，长音频是硬阻塞 | FFmpeg 按 300s 切片，逐片转写 |
| 一次调用传超长音频 → 表面成功但结果截断（隐性故障） | 分片 + 每片判空校验，空片不算完成 |
| 转写到 28 分钟挂掉，整段重来 = 之前全白做 | 片级持久化：失败只重跑失败片，已完成片复用 |
| 恢复耗时与"视频总长"绑定 | 拆片后恢复耗时只与"失败片数"绑定 |

#### 3.3.4 逐环节拆解（为什么这么设计）

**① 为什么 300 秒？** 对齐 ASR 单次调用的**硬上限**：10MB / 音频时长上限以内再留余量。为什么不是一个更长/更短的值——更短则调用次数和成本翻倍；更长则超限喂不进去。300s 是在"限制内 + 不过度拆分"之间的平衡点。**口径要点：这是受约束设计，不是拍脑袋参数**。

**② 分片的双重收益**：技术上满足输入限制（第一层），工程上获得失败局部化（第二层）。面试被问"为什么分片"时，两层都答出来。

**③ 片级状态如何落库（为什么能复用）**：每个片段在 `transcription_chunk` 表一行，状态字段 pending/running/completed/failed + 该片原文。重试/重启消费者时 `completedTranscriptionChunk(taskID, i)` 命中 completed 且内容非空的片 → 直接跳过，指标 `asr_chunk_reused` 真实打点。

**④ "空片不算完成"**：`text != ""` 才 `markCompleted`；空结果按缺陷处理，避免"成功但没字"的假成功混进转录本文。

**⑤ 与 3.2 的关系（三层可靠性栈的第 3 层）**：
```
job 层：processing lease → "整个任务不被并发执行"
消息层：成功才 commit → "任务不因消费侧崩溃丢失"
片级：片状态持久化 → "任务内部已完成的片段不重算"
```
话术再强调一遍：**同一条"失败可恢复"的思路，投递、执行、片段三个粒度各做了一遍**。这句是 3.3 的灵魂。

#### 3.3.5 追问演练

- Q：怎么切片的？→ `ffmpeg -f segment -segment_time 300`，产出编好号的一组 mp3。
- Q：重试时怎么知道哪些片完成了？→ 查 `transcription_chunk` 表，status=completed 且内容非空才**复用**；只重跑缺失/failed 的片。
- Q：某一段永远失败呢？→ 该片失败让整个任务失败进入重试（重试同样只跑失败片）；多次重试耗尽进 Dead，用户可删除/重新触发。诚实口径：任务是整段失败，成本上是"仅缺失片"的成本。
- Q：一段视频转写出来多少片？→ 按 300s 一刀，取决于视频长度（如 30 分钟 ≈ 6 片）。
- Q：怎么拼回去？→ `parts` 以 `\n\n` 连接成完整转写。

#### 3.3.6 边界（别踩）
- 简历没有"恢复耗时下降 X% / ASR 调用减少 X%"的量化，**别编**。被问变化量：答"量级上只跟失败片数相关"，诚实。
- 300s 是"项目的分片粒度"，不是全行业的统一值；面试官若质疑，回"以 ASR 供应商的硬限制为基准定的"。

### 3.4 RAG 多阶段检索 + MRR + 引用片段（重点-lite）

> 简历：基于 pgvector 构建多视频 RAG 知识库，针对用户问题表述模糊、单路召回覆盖不足与候选排序偏差，构建 Query Rewrite、多查询向量召回与 Rerank 的多阶段检索链路，使 MRR@5 从 0.78 提升至 0.93，并通过返回引用片段增强问答可追溯性。

#### 3.4.1 故事稿（45s，这条最值钱）

> 知识库是"多视频"的，用户问题通常说不清是哪一段。第一版只有单路向量召回，三类问题撞墙：①问题表述模糊（"讲讲那个并发的部分"，转写里没有"并发"二字）；②答案依赖多个片段组合，一路召回漏掉一部分；③召回了但排序不对，正确答案在第 3 名，模型拿到第 1 名的错片段就答错。所以我加了三个环节：用 LLM 把问题做 **Query Rewrite**（**永远保留原问题**兜底），对每条改写做**多查询向量召回**，用 RRF 融合跨查询结果，最后用 **Rerank** 精排把最相关的顶到第 1 名。在自建的困难问题集（30 条语义/细节类）上 MRR@5 从 0.78 提到 0.93。同时回答里带 `[Cx]` 引用，映射回真实片段，前端可点击核对——回答不是编的。

#### 3.4.2 概念地基（"人话"表）

| 概念 | 人话 |
|---|---|
| RAG | 不直接干问大模型，先检索出相关片段拼进 prompt 再问；回答被约束在证据内、可溯源 |
| 为什么不能整段塞给 LLM | 技术层：上下文窗口上限，长视频转写几万~几十万字塞不下，塞进去又贵又慢；效果层：相关线索被淹没在无关文字里，注意力稀释，反而答不准 |
| chunk | 转写切成的小块。本项目 800 字一块、相邻 120 字重叠（防句子恰好在边界被切断） |
| embedding | 把文字转成语义向量，语义相近的词向量相近 → 搜索从"关键词匹配"升级为"语义匹配" |
| pgvector | PostgreSQL 的向量扩展：向量和事实数据同库存、同库查，不必养单独的向量库 |
| 候选集（candidate/topK） | 先粗捞 30 条"可能相关"，再精挑 5 条给模型（粗排→精排两层） |
| Query Rewrite | 让 LLM 把模糊、口语、带指代的问题改写成更"检索友好"的问法 |
| 多查询召回 + RRF | 同一问题多个问法各搜一遍，用"倒数排名融合"合并去重 |
| Rerank | 粗排只管"可能相关"，Rerank 对候选打分精排，把最相关那条摆到第 1 |
| 引用片段 / fail closed | 回答标注来源可核对；没有索引就不答题（宁可不知道，不编） |

#### 3.4.3 痛点 → 方案（三个痛点、一一对应，这是简历的骨架）

| 痛点 | 方案 | 类比 |
|---|---|---|
| ① 问题表述模糊（"讲讲那个并发的部分"） | Query Rewrite 改写检索式 | 搜不到就用更准确的关键词重新搜一遍 |
| ② 单路覆盖不足（答案依赖多片段） | 多查询向量召回 + RRF | 多个人不同说法各搜一遍，合并去重 |
| ③ 找得到但排不对（正确在第 3 名、模型只认真看第 1 名） | Rerank 精排 | 粗捞回一批，再由精读的人挑出真正对的放最前 |

#### 3.4.4 逐环节拆解（为什么这么设计）

**环节 ① Query Rewrite**
- 到底改什么：用户"那个讲并发的"，转写里只有"goroutine / 同时执行"。改写把它变成能命中的检索式。
- 怎么做：调 LLM 产 JSON `{"queries":[...]}`（最多 3 路），然后 `stableRewriteQueries` **永远把原问题也并进去**（`rag_rewrite.go`）。为什么：改写可能改坏/跑偏，原问题是最稳妥的一路，不允许改写覆盖正确方向。
- 不选的其他方案：直接让 LLM 看全文答 = 放弃检索（塞不下 + 不可溯源）；词面关键词改写（分词）解决不了"并发 vs 同时执行"这种中文语义鸿沟。

**环节 ② 多查询向量召回 + RRF**
- 解决什么：一个问题对应多个事实点，单路召回只想起一个方向，漏方向答案就不完整。
- 怎么做：N 条查询分别去 pgvector 粗捞，得到 N 个 candidate 列表，**RRF（倒数排名融合）**合并：同一候选出现在几路里、名次靠前 → 融合分高。天然同时解决"去重"和"合并"。
- 为什么不直接比分相加：各路分数在同一个 embedding 空间里，相关片段的分数可能互相打架（偏爱某路）；RRF 只看**名次**不看分数，鲁棒，是混合检索的业界默认融合手段。

**环节 ③ Rerank**
- 解决什么：粗排保证"相关的基本都在"，但第 1 名 vs 第 3 名谁更相关粗排分不出来，而模型只认真看第 1 名。
- 怎么做（两种，记住差别）：
  - **DeterministicReranker**（线上默认）：不调模型，以 `RRFScore` 为底分，加查询词覆盖度、片段来源（vector/keyword 差分）、相邻片段连续性，做**小幅修正而非推倒重排**。快、稳定、零外部依赖。
  - **ModelReranker**（配置 `rerank_model` 才启用）：调 cross-encoder（本项目 Qwen3-Reranker-4B）对候选和问题算 relevance 分重排。精度上限更高，代价是外部调用延迟 + 失败风险。
- 为什么线上默认 deterministic：评测里 rerank 的收益本质是"把一条本该靠前的位置修正回第 1"这种位置修正，deterministic 就够，还便宜。model 是显式覆盖路径——**不是 AI 调用越多越好，这是评测驱动出的保守选择**。

**数据链路合成（背下来）**：
```
用户问题
  → Query Rewrite（最多3路，永远含原问题；失败回退原问题）
  → 多查询向量召回（每路去 pgvector 粗捞 top30）
  → RRF 融合（跨查询合并去重）
  → Rerank 精排（deterministic 默认 / model 可选）
  → top5 片段
  → 组装 prompt：'[C1]片段1\n[C2]片段2...\n问题：xxx' → LLM
  → 回答带引用 [Cx]，映射回真实片段（buildCitationSet）
```

#### 3.4.5 引用片段 + fail closed（为什么是设计不是回显）

- 解决什么：RAG 最大的信任问题是"模型是不是又在编"。只说答得好，用户没法验证。
- 怎么做：prompt 里给片段编号 `[C1]…` 并规定"按证据回答、引用用编号标注"；回答后把编号映射回真实片段（`buildCitationSet`）成 `Citation`（含 task_id、video_title、chunk_index、内容、各检索环节名次），前端渲染成可点击引用。
- **诚实细节**：目前没有时间戳字段，引用粒度是"哪一段转写块"，不是"第几分几秒"——这是已知缺口（`chat_prepare.go:98` 注释里标记了），被问就说"时间戳定位是下一步"。
- **fail closed**：`strict_rag` 模式下视频没建索引/检索不到上下文就直接拒绝回答（"当前视频尚未构建 RAG 索引"），不硬答。宁可说不知道，不说编一个——防幻觉最硬的闸。

#### 3.4.6 可靠性细节（fallback 表，背住）

| 环节挂了 | 怎么办 | 为什么能降级 |
|---|---|---|
| Query Rewrite 超时/失败 | 回退原问题检索 | 原问题永远在查询集里 |
| Rerank 调用失败（model 档） | 保留原向量候选顺序 | 粗排已够用，rerank 是顶配 |
| 视频没有 RAG 索引 | fail closed 不答 | 比幻想要强 |
| 回答引用越界/无证据 | constraint 校验 + 追加"以下结论无证据支撑"标注 | 极度诚实，不撒谎不删证 |

话术：**"任何单点失败都不让链路退化到瞎编。"**

#### 3.4.7 追问演练（含数字口径）

- Q：0.78→0.93 怎么来的？→ §0 答疑卡：困难问题集 30/45 条，0.778→0.933，本地 dev 集，非线上显著。主动带口径 = 加分。
- Q：为什么不用 BM25 混合检索？→ 做过：中文 n-gram 分词噪声 + 等权 RRF 把正确的向量结果挤出 Top5（MRR 0.845→0.826 反而降），所以生产关闭 BM25，走"向量为主 + 改写 + rerank"。"评估过并主动关掉"比"吹混合检索"可信得多。
- Q：Query Rewrite 很慢怎么办？→ 诚实：大投入，45 条完整跑 P50 8.3s / P95 16.8s（多家 AI 调用）。三处兜底：失败回退原问题、fallback 计数监控、规划按问题复杂度选择性启用改写，不冤枉简单问题。
- Q：rerank 挂了？→ 回退到原向量候选顺序，链路不崩，有 `rerank_failed_vector_baseline` 指标打点。
- Q：怎么防止用无关片段？→ 索引缺失 fail closed；`[Cx]` 映射真实 chunk 供前端核对；spec-07 约束引用编号在候选集内。
- Q：pgvector 用什么索引？→ 诚实：当前 1536 维、brute-force cosine 排序（几百~几千 chunk 量级线性扫描够用）；数据量上来再上 HNSW，这是明确优化方向。**别吹用了 HNSW**。
- Q：怎么防幻觉？→ 三层：只答检索到的上下文（fail closed）、引用可核对、无证据结论显式标注。诚实说防不到 100%，目标是"可验证 + 不静默编造"。

#### 3.4.8 架构级 why（串起来回答"为什么是这套设计"）

1. **粗排→精排两层分离**：粗排管"查全"（30 条候选），精排管"查准"（top5 第 1 真最相关），模型只承担精排后的回答。
2. **多环节串行只为迁就"一个问题多个难点"**：模糊→改写；覆盖→多路；排序→精排。每环只解决一类坏情况，不是炫技。
3. **为什么非 RAG 不可**：视频内容是动态新增的私有数据，模型不知道；检索让系统"永远基于最新证据回答"且"每句可溯源"。
4. **pgvector 而非独立向量库**：当前量级同库最省运维、事务天然、事实源与投影同库可原子重建；真到千万级再上专业向量库/HNSW——量级驱动选型，面试官很吃。

**被问"怎么改进"（三个真缺口，代码里有痕迹）**：时间戳定位（精确到分钟/秒）；按问题复杂度选择性启 Query Rewrite；量级上来上 HNSW。

**自我检查话术**：被人问"你这个 RAG 和网上 demo 有啥区别"——
> 我把它当一个**要上线的工程**来做：有明确的三个失败场景（模糊/覆盖/排序），每个对应一个环节，每个环节都有 fallback，没有索引直接拒绝回答——不是搭个 demo 展示"会"，而是想清楚"挂了怎么办"。

#### 3.4.9 边界（别踩）
- 0.78→0.93 必须带"困难问题集、本地、非线上显著"口径（§0）。
- 不说 model rerank 一定提升 / 答案准确率提升 / "用了 HNSW" / BM25 全开。
- 引用粒度目前是 chunk 级无时间戳，别吹精确到秒的定位。

### 3.5 AI 摘要（简介 + bullet 2 提到的能力，补全篇）

> 简介：支持…AI 摘要…；bullet 2：引入 Kafka 异步调度 ASR、**摘要生成**和 RAG 索引等长耗时任务。摘要不在简历四号位，但出现在两处，被问一句要有得说。

#### 3.5.1 故事稿（20s）

> 转写完成后，我把它交给 LLM 生成一份**结构化摘要**（核心摘要、深度洞察、原始内容精选、领域标签，Markdown 格式），单独存表、前端直接渲染。它和转写、索引一样走 Kafka 异步 + 状态机 + 退避重试（同一套 3.2 机制）。另外我用**文件内容指纹（file_md5）做去重**：同一个视频不管谁触发、触发几次，都只真正调一次模型，后续用户直接复用结果，省的是真实的 API 成本。

#### 3.5.2 概念地基

| 概念 | 人话 |
|---|---|
| 结构化摘要 | 不是把长文缩写成短文，而是按固定结构产出（核心摘要/洞察/精选/标签），前端才能排版渲染 |
| 复用转写 | 摘要的输入是已落库的转写全文，**不做第二次 ASR**（ASR 才是贵的） |
| 内容指纹去重 | 以文件的 MD5 做去重键：同一内容跨 task、跨用户只有一个成功结果行，行存在即 Completed 语义 |

#### 3.5.3 痛点 → 方案

| 痛点 | 方案 |
|---|---|
| 摘要依赖 LLM，和转写一样是分钟级外部调用 | 放同一套异步任务（`video-analyze`）+ 状态机 + 退避 |
| 同一视频被多次分析 = 重复花钱调模型 | `file_md5` 内容指纹去重：只跑一次，后续复用 |
| LLM 关键时刻不可用，问答可能没有摘要可用 | 问答侧有降级：检索片段 + **已有摘要**直拼（spec 06 档2，`degraded:true`） |

#### 3.5.4 为什么要这样设计
- **为什么复用转写而不重做 ASR**：摘要的成本与延迟大头在模型调用；ASR 一次几十分钟，绝不为摘要再跑一遍。管线里"转写产出"被三个下游共享（摘要 / RAG 索引 / 问答），这是"一次转录、多方消费"的设计。
- **为什么独立存表 + TEXT + Markdown**：AI 结构化输出与转录业务解耦（`model/summary.go` 注释原话："面试亮点：独立存储 AI 结构化输出"）；`text` 大字段存 Markdown，前端不用拼 JSON 直接渲染。
- **为什么去重键用 file_md5 而不是 task_id**：task_id 是每次上传一个；内容去重要跨 task、跨用户——两个用户传同一个视频（内容相同）只该有一份分析结果。这是与 RAG 一脉相承的"内容即成本"思路：**能复用就不重跑**。

#### 3.5.5 追问演练
- Q：摘要用什么生成的？→ 复用转写的全文，调 LLM 做一次 chat completion，prompt 规定输出结构（核心摘要/深度洞察/原始内容精选/领域标签）。
- Q：同一视频两个用户都触发分析？→ `file_md5` 唯一索引去重，只真正跑一次模型，第二个直接用已存结果。
- Q：摘要调 LLM 失败呢？→ 走异步重试（60/300/900s），多次失败进 Dead 可重新触发；问答侧另有"已有摘要直拼"的降级路径，不让 LLM 挂了连句正常话都答不出。
- Q：摘要和 RAG 索引的关系？→ 不互相依赖：摘要基于全文生成；RAG 索引基于分块 embedding。两者独立，各自消费转写产物。

#### 3.5.6 边界
- 摘要不承担简历主叙事，**被问才讲，别反客为主**。
- 不吹"摘要质量/准确率"——没有对应评测数字。
- 别把"省成本 X%"当 claim，去重是事实，但没有量化出"省了多少"。（项目相关 tie-in）

- **"为什么用消息队列？"** → §3.2：跨进程、长耗时、需恢复；不是为 MQ 而 MQ。
- **"Kafka 怎么保证不重复消费？"** → 消费查状态幂等 + DB 状态 CAS + 成功才 commit + message dedup 两层。
- **"Redis 事务/一致性？"** → 分片状态用 TxPipeline 原子写多 key；合并互斥用 Redis 锁；说明这是"弱一致可容忍场景"的取舍。
- **"数据库设计/为什么 PostgreSQL？"** → 事实源（task/transcription/chunk/asset）+ pgvector 同库；向量是投影，可重建。
- **"哪部分是同步的？"** → 上传、check/merge、登录、问答检索是同步；ASR/摘要/索引异步。会画这条分界线说明真懂异步边界。
- **全栈方向：前端做过什么？** → 展示面 + 校验面：Vue3（现在在重写 Next.js）——分片上传进度、流式问答（SSE 增量渲染）、引用片段展示、任务状态轮询。老实口风：前端主要承担校验与展示，重心和难点在后端架构。被问前端细节就讲 SSE 解析（`EventSource` 带不了 Authorization header，所以手写 fetch + ReadableStream 解析 `text/event-stream`）+ 进度 UI（`web-next/lib/api.ts:131-194`）。

### 8.2 指标与检索算法：定义级理解

**指标（简历出现的全是这些，公式要能说出来）**
- **MRR@5（Mean Reciprocal Rank）**：每个查询"第一个正确答案所在位置"的**倒数**，取平均；@5 表示只在 1~5 位里数，没进前 5 记 0。例：答案在第 2 位 → 该查询贡献 1/2。简历里 0.78→0.93 就是这个指标在困难集上的变化。
- **Recall@5**：正确答案排进前 5 的查询占比（"查全率"视角）。基线的 Recall 本来就高（93%+），所以**项目最终主要观察 MRR 和 Hit@1，而不是只看 Recall**——这句面试官追问时主动说。
- **Hit@1**：答案恰好排第 1 的占比。
- **nDCG@5**：按相关位置算的排序质量，位置越靠前加权越高、归一化。评测报告里用来衡量"排序本身好不好"。

**算法（知道这三对就够）**
- **bi-encoder vs cross-encoder**：这是"检索分两步"的根本原因。
  - bi-encoder：query 和 document **分别**编码成向量（互不干扰，文档向量可提前算好存起来）→ 检索用，支持大规模、毫秒级，但**对"句子对"的精细关系不敏感**。本项目 embedding（text-embedding-3-small，1536 维）是这一类。
  - cross-encoder：把 query+document **拼在一起**整体编码，能精细建模两者关系但**每次都要重新算、不可预计算** → 精排用，数量上只敢用于 top-30 候选。本项目的 Rerank 是这一类。
  - 结论话术：**所以检索天然是"bi-encoder 粗捞候选 + cross-encoder 精排"，不是谁更聪明，是成本结构决定的**。
- **RRF（Reciprocal Rank Fusion）公式**：候选片段的融合分 = Σ（1 / (60 + 该片段在这一路里的名次)）。只吃"名次"，不吃"分数"——所以能用在不同来源/不同量纲的结果之间。同样的片段被多路命中、名次越靠前，分越高。
- **embedding 相似度怎么比**：余弦相似度；pgvector 里 `<=> ` 运算符就是余弦距离，`ORDER BY embedding <=> $1 LIMIT` 即向量近邻检索。

### 8.3 Kafka 底层三词（顺着 3.2 往下钻必答）

| 概念 | 一句话 | 和本项目的关系 |
|---|---|---|
| partition（分区） | 一个 topic 拆成多个分区，消息分散在分区上，消费端才能并行 | 本项目一个 topic 一个消费者（video-transcribe 等）；同一任务的流转天然串行，**对顺序不敏感**——如果被问到"怎么保序"，实话说"我们按任务类型分 topic、单任务串行流转，没做 key 级分区，任务间无序不影响正确性" |
| consumer group（消费组） | 组内**一个分区同一时刻只被一个消费者**处理；重平衡(rebalance)时实例间重新分配分区 | 这就是"处理中保证不重"的底下那层；但组内不重 ≠ 消息不重投（下方 at-least-once），所以仍要 task 状态 + lease（§3.2）收口 |
| at-least-once（至少一次） | Kafka 默认语义：**已提交的消息不会丢，但可能重复投递** | 这一条直接解释 §3.2 整节：因为可能重复 → 必须有幂等/去重/手动 commit；因为不会丢 → 任务状态可以放心以 DB 为事实源。**面试里把这条因果链讲出来，比背任何概念都有力** |

**把这三词串成一段"为什么你的设计是对的"**：
> 消息队列是 at-least-once 的：不丢，但可能重复。所以我不能依赖"消费端天然只处理一次"——我用任务状态机（DB 事实源）判重、用 processing lease 保证只有一个人干活、成功才 commit。重复我兜得住，丢失我兜得住，这正好让 Kafka 来承担"不丢"，剩下的"不重"由我自己的状态层补上。

### 10.1 真题一：怎么保证分片上传的文件一定是正确的？

**先想清楚（思考框架）**：正确性拆成两层，威胁模型不同——
- **完整性（completeness）**：该传的片段都到齐了，齐了才允许合并。威胁：缺片、换文件。
- **一致性（integrity）**：到的东西是对的、没坏。威胁：传输损坏/位翻转（误码）、恶意篡改。

面试被问时把这两层分开说，框架感立刻出来。

**手册口径（现状，诚实）**：完整性这层现在做得很扎实——上传前先登记文件规格（file_size/chunk_size/total），规格不一致（比如中途换文件）自动重置；合并前服务端在互斥锁下逐片确认都在；`ComposeObject` 后 size 必须 == 期望值，否则删产物报错。一致性这层目前是"每片字节数 == chunk_size + 合并总大小校验"。

**教科书升级设计（面试官想听的方向）**：一致性再加两层——
1. **每片 hash 校验**：上传时对每个分片算哈希，服务端比对后确认已收到，损坏/篡改的片在合并前就被拒。
2. **合并后整文件哈希比对**：客户端传来整文件哈希，服务端对合并产物再算一次，相等才通过。
3. **一条加分小知识**：防篡改用 **SHA-256**，不要用 MD5——MD5 只防误码（checksum），SHA-256 才防恶意篡改。面试里主动点出这句区分是明显加分。业界类比：S3 MultipartUpload 用 ETag 就是这个道理。

**权衡（被问"代价呢"）**：每片多一次哈希计算，MB 级数据的 SHA-256 现代硬件下很快，值得；但"期望哈希从客户端来"本身有信任假设——客户端可自报哈希，真要防恶意上传得服务端另验或可信客户端。通常场景它是**完整性校验**而非安全边界，这样说最严谨。

**话术（60s，三段式）**：
> 我把"文件对不对"拆成两层看：一类是**完整性**——该传的片都到了没有；一类是**一致性**——到了的片是不是完好的。完整性现在就有：上传前先登记规格、规格不一致会重置、合并前逐片在锁内确认、合并后总大小必须等于期望，对不上就删产物报错。一致性这一层，目前做的是每片大小校验加合并总大小校验；如果再硬一层，我会给每个分片上 SHA-256、合并后拿整文件哈希和客户端比对——注意是 SHA-256，因为 MD5 只能防传输误码、防不了恶意篡改，这个区别在日常工程里很常见。代价就是每片多算一次哈希，几 MB 的数据量下几乎可以忽略，收益是坏片在合并前就拦下来，而不是等到整文件比对才发现是哪块坏了。

**追问演练**
- Q：拿 Redis 当进度事实靠谱吗？→ Redis 是**进度代理**，真正的资产事实在 MinIO + PostgreSQL；Redis 丢了只是丢进度，分片还在，可重建。
- Q：客户端自己报哈希怎么防恶意？→ 诚实：客户端报的哈希是校验我们用，防"坏片"；防"恶意"需要可信源或服务端二次验证，超出分片场景的默认威胁模型。别吹成安全边界。

### 10.2 真题二：外部 AI 调用成功但系统没落库，误判失败而重试 → 二次调用、二次扣费，怎么解？

**先想清楚（核心洞察，说得出这句就赢一半）**：
> 这个问题的本质是**外部调用的副作用（扣费）发生在我的系统之外，它返回成功的那一刻钱已经花了；而系统内的落库是之后才发生的**。所以任何"先调用、后记状态"的流程都有这条缝隙——调用成功、写库失败、判失败、重试、再调一次、再扣一次。

**解法：一句话原则 + 四个层次**
- **一句话原则：结果即事实（persist the response first）**——provider 的响应在返回的那一刻就要先持久化下来（以 task+chunk+请求指纹为键），重试时命中结果行就直接复用，**根本不发第二次调用**。这跟 3.3 的"片级复用"是同一个思路，只是把复用的"结果落库"提前到响应返回时就做。
- **第 1 层（防二次调用）**：响应先落库 + 复用。去重键 = task_id + 片段索引 + 请求内容指纹；失败重试先查这个键。
- **第 2 层（provider 侧幂等）**：支持 `Idempotency-Key` 的 provider，第二次同键调用返回缓存结果、不重复计费。我们记账表里已经有幂等键（`ai_usage_ledgers.idempotency_key` 唯一索引），把这个键透传给 provider 就是同一套设计。
- **第 3 层（就算调第二次，也不重复扣费/超量）**：这条**代码里已经有落地**，面试可指认——
  - 每次 AI 调用都记 `ai_call_logs`（kind/status/tokens/estimated_cost/failed），异常一目了然；
  - `ai_usage_ledgers` 用**唯一幂等键**记账：二次调用不会导致账单双倍；
  - `ai_retry_budgets` 是**提供方重试和调度器补投共享**的 attempt 预算 + 截止时间，重启不会重置额度——最坏情况的重试次数被钉死（assignment 注释原文："provider 和 task-scheduler 重试消耗同一个计数，restart 不能静默造出新的重试额度"）；
  - `quota_compensations` 是协调 Redis 日额度与 PG 账本的 durable outbox，带幂等键 + lease + 重试。
- **第 4 层（把缝隙本身钉死）**：故障注入测试专门注入"provider 成功但落库失败"，验证它不产生二次计费（仓库里有 `internal/mq/fault_matrix_test.go`）。

**话术（90s，先说洞察再说四层）**：
> 这个问题的本质是外部调用和内部状态之间的时差：ASR 或 LLM 返回成功的那一刻，扣费已经发生了，而我把结果落库是之后的事——所以"先调用、后记状态"的流程必然有这条缝隙。我的原则是**结果即事实**：provider 的响应一回来就先持久化，按键=任务+片段+请求指纹，重试先查有没有已落的结果，命中就直接复用，根本不再发第二次调用。这是第一层。第二层，支持幂等键的 provider 复用同一请求键，第二次调用返回缓存结果不重复计费。第三层，就算真的调了第二次，系统也不能被双重算账——我们的 AI 调用有全量 call log，usage 记账走唯一幂等键，二次调用不会让账单翻倍；而且提供方重试和调度器补投共享同一个 attempt 预算和截止时间，重启也重置不了，最坏情况的重试次数是被钉死的。第四层，我用故障注入把"provider 成功但写库失败"这个场景专门做成测试，确保这条缝隙永远不会静默产生二次计费。所以这类问题不是靠"多试试"解决，是靠"把'扣过费'这件事先固化下来 + 记账侧幂等 + 重试有界"三层一起兜。

**追问演练**
- Q：响应先落库会不会引入新的一致性问题？→ 会，但它把一致性收回到"一个持久化步骤"，失败可以安全重试；代价小、收益是彻底消除"重复扣费"这一类。
- Q：provider 不支持幂等键怎么办？→ 那就靠第 1 层和第 3 层兜：响应先落、记账幂等、预算有界。幂等键是锦上添花，不是必需。
- Q：这和 3.3 的片级复用是什么关系？→ 同一个思路的两端：3.3 是"完成态持久化、失败重跑缺失片"；这里把"结果落库"提前到响应返回那一刻，让复用窗口从"重试前"变成"重试时"。
- Q：你说重试预算共享，能解释一下吗？→ provider 内部重试和我们的调度补投共用同一个 `ai_retry_budgets` 计数 + 截止时间，防止"provider 试了几次放弃、调度器又新开一轮"这种叠加放大；重启也不会重置。**
